# rmm — Rust Mod Manager: specification

A fast, beginner-friendly mod manager for **Skyrim SE/AE and Fallout 4** on **Windows**. Linux and Steam Deck support (Proton, a FUSE view of Data) is written and tested in WSL but on hold, so rmm is Windows-only for now (see M6). It combines MO2's control with Vortex's ease of use. It can be driven completely by an AI over **MCP**, including in-game testing, and it has an **add-on system**.

Design inputs come from `reports/Skyrim and Fallout 4 mod managers.md`. The main lessons:
- People leave Vortex because it lacks drag-and-drop file priority and its rules can form cycles.
- People avoid MO2 because of its learning curve and the time its virtual filesystem adds to every launch.
- Nobody ships whole-setup undo, conflict views inside BSA/BA2 archives, or lockfile-style setups.
- Migration cost keeps users on their current manager.

## Principles

1. **The core library is the product.** The CLI, the MCP server, the Tauri UI and add-ons are thin shells over `rmm-core`. A capability exists once and every shell gets it.
2. **Every change can be undone.** Mod files are immutable once installed, so a setup is just a small text state. Every mutation snapshots that state first. Undo is whole-setup and also covers changes made by the AI.
3. **Show before writing.** Every operation that touches the game folder computes a plan first (`dry_run`), then applies it. The plan is what the UI shows and what the AI reasons about.
4. **Game folder is never lost.** Deploys write a manifest. Vanilla files that get overwritten are backed up. Files changed outside the manager are captured, never deleted.
5. **Beginner surface, expert depth.** The default view is mods plus a Play button. Conflicts, rules, output routing and per-file overrides appear only when they are needed.

## Data model (portable instance folder)

```
<instance>/
  instance.toml          game, game_path, local_path (plugins.txt dir), active profile,
                         ini_path and downloads_path when set
  mods/<id>/             installed files, immutable; Data-relative, plus root/ for game-root files
  mods/<id>/rmm-mod.toml name, version, source (nexus ids, archive hash), fomod choices, notes, categories
  mods/<id>/.rmm-index   cached file list for fast conflict scans
  profiles/<name>/profile.toml   ordered mod list (last wins) + plugin order + active plugins
                                 (`shared_order`: profiles in one group share their mod and plugin
                                 order, each with its own enabled ones; `rmm profile share-order`)
                                 + row colours + plugin locks
  profiles/<name>/history/       numbered snapshots for undo/redo
  profiles/<name>/ini/           the profile's own game INIs, when it keeps them
  profiles/.deleted/<name>/      the last deleted profile of each name
  profiles/<name>/bisect.json    a search for the mod behind a crash, while one is under way
  overwrite/             captured output from tools and the game; deployed above every mod
  backup/                vanilla files displaced by deploy
  ini-backup/            the user's own game INIs while a profile's are in My Games, and
                         their plugins.txt while rmm's is deployed
  game-version.txt       the game's version at the last Play, to notice game updates
  ini-state.json         which profile's INIs are in My Games, the save path rmm replaced,
                         and whether the user had a plugins.txt
  trash/                 uninstalled mods and the old files of updated ones (so undo can restore them) until Empty trash
                         (History tab, `rmm trash --empty`) deletes them for good
  rules.toml             mod rules (load after, requires, incompatible), shared by every profile
  addons/<name>/         add-ons: addon.toml + addon.wasm (see "Add-ons")
  nexus-cache.json       answers from Nexus update checks (see "Nexus Mods")
  nexus-requirements.json  what each Nexus mod's page lists as required
  nexus-updates.json       what the last update check found, for the mod list's Update tags
  support/               support bundles (`rmm-support-<time>.zip`) saved without a folder picked
  nexus-categories.json  the game's category names on Nexus, read once when signed in
  modlist.lock.toml      the setup written down by export_lockfile (see "Import and lockfiles")
  test-runs/<time>/      screenshots from test runs (see "In-game test harness")
  deploy.json            manifest of what is deployed where
  .lock                  write lock shared by UI, CLI and MCP
```

**Mod order** uses MO2's model: one list that you drag and drop, where the last entry wins. **Separators** are entries in that list with ids starting `sep:` (no mod id can contain `:`). Each heads the mods after it, up to the next separator. They hold no files, are never enabled, survive profile switches, and their colours live in `profile.toml`. Moving a separator in the window moves its whole group; the core moves exactly the ids it is given, as one block in list order (`move_mods`). **Rules** use Vortex's model, but only as *constraints and suggestions*. The UI warns when the list breaks a rule and offers an "apply rules" sort. Rules never block manual ordering, so they can never trap the user in a cycle.
  - A rule says a mod loads after other mods, so it wins their file conflicts (Vortex's "load after"; "load before" is the same rule seen from the other mod). Rules live in `rules.toml`, keyed by mod id and shared by every profile. `set_mod_rule` (CLI `rmm mod-rule <id> --after X`) replaces a mod's rule and returns the previous one, since rules are not in a profile's undo history.
  - A rule can also say a mod **requires** other mods (they must be enabled when it is) or is **incompatible** with them (they must not be enabled together). `health_check` reports both as errors, and reports each load-after rule between enabled mods that the order breaks.
  - A new mod goes where the rules put it: at the end, before a trailing run of generated tool output, and before any mod whose rule says it loads after the new one.
  - `sort_mods` (CLI `rmm sort-mods`) is a stable topological sort: it takes the mods in their current order and holds a mod back only until the mods it loads after are placed, so an order that already follows the rules doesn't change. Rules that form a cycle are found first; one rule per cycle is left out and reported. Applying the sort is undoable.
  - A tool run that replaces its generated mod moves rules over to the new mod id.

**Archive conflicts** follow the game's rules. A mod's BSA/BA2 is loaded only when an enabled plugin is named after it: `<plugin>.bsa` and `<plugin> - Textures.bsa` on Skyrim SE, `<plugin> - *.ba2` on Fallout 4, the same rules as libloot. Archives load in plugin load order, and a file in a later archive replaces the same file in an earlier one. Any loose file beats every archive, even one from a lower-priority mod. `list_conflicts` reports the archived files and who replaces them next to the loose-file conflicts. The health check flags mod archives that no enabled plugin loads. Only headers and name tables are read (`rmm-core::archives`); Fallout 4's 125,000-file `MeshesExtra.ba2` lists in a quarter of a second.

**Plugin order** is stored per profile. Plugins are discovered from the enabled mods plus vanilla `Data`. `plugins.txt` is written at deploy time through libloadorder. The first write keeps the user's own `plugins.txt` (from another manager or the game's launcher) in `ini-backup/`, and a purge puts it back, or removes rmm's when the user had none. A plugin can be **locked** to its position (`lock_plugin`, MO2's index lock): sorts, moves and installs leave it there, and the window says so when a move would. An install adds a mod's new plugins at the end, each after the ones from the same mod it's built on (its masters), so a patch never lands before the plugin it patches. The `missing_masters` finding tells a master that is on but loads later ("loads before …") from one that is missing or off.

**Mod details.** A mod can be renamed (`rename_mod`; its id and folder stay) and given notes (`set_mod_note`, kept in `rmm-mod.toml`); any row can take a colour (`set_color`). **Categories** are labels like MO2's (`set_mod_categories`, `rmm category`, kept in `rmm-mod.toml`, not undoable, like notes). A mod with none of its own shows its Nexus category (its id recorded at a Nexus install or MO2 import, the name from `nexus-categories.json`); the first edit keeps that one, and removing every label leaves none. An MO2 import brings MO2's categories by name (`category=` in meta.ini, names from the instance's `categories.dat`) and the Nexus category (`nexusCategory=`). `reinstall_mod` installs a mod again from the archive or folder it came from, optionally with new FOMOD choices, keeping its place. `update_mod` (`rmm update`, the panel's **Update…**) does the same from a newer archive or folder: the mod keeps its id, name, place, enabled state, notes, categories, colour, rules; its Nexus ids become the new archive's when that says them (MO2's .meta beside it, a download rmm fetched or identified, or a Nexus file name), so update checks don't offer what's now installed, and a FOMOD installer opens with the stored choices. Installing a file that is another version of an installed mod (the same Nexus mod id, from the download or the file name Nexus gives it) offers Update or Install as a new mod. When several installed mods came from that page (MfgFix and MfgFix MCM), only the one whose file has the same name is offered; if no name settles it, there's no offer. Both put the old files in `trash/.replaced/`, and their history entry records the swap, so undo and redo trade the folders back until the trash is emptied; the mod's name, notes and categories stay as they are. `overwrite/` can be turned into a mod (`mod_from_overwrite`, undoable) or cleared to `trash/overwrite`.

**The mod panel** shows, besides the above, what MO2's information dialog does. It gives the version, or for a Nexus mod a **Nexus page ↗** link, a **Needs** section and an **On Nexus** section. **Needs** lists what the mod's Nexus page requires, as last read (`mod_details`' `needs`), each marked installed, turned off, not installed (a link to its Files tab), a DLC or from another site, with the author's note; until the page was read it offers **Read it from Nexus** (no key). The mod rules below it are headed "(your rule)", with "No rule." when empty, so they don't read as what the mod needs. That section's **Show its description** reads the page (`nexus_mod_info`, no key) for its summary, picture, author, endorsements, last update and description. The window's CSP lets pictures in from `staticdelivery.nexusmods.com` only. The section also lists the mod's read-me's and settings (`.txt`, `.md`, `.ini`, not `Interface/Translations/`), which open in a wrapped viewer, and its pictures (`.png`, `.jpg`, `.gif`, `.webp`, `.bmp`, up to 24 shown on **Show them**, 8 MB each), larger on a click. `mod_details` lists the first two as `docs` and `images` (50 each), so an AI sees them too.

**File-level hygiene.** `move_files` (`rmm move-files <from> <to> <paths>`, Overwrite's **Move to mod…**, the panel's **Move files…**) moves files or folders from a mod, or Overwrite (`<overwrite>`, `overwrite` on the CLI), into another: MCM settings into a settings mod, a tool's output into the patch it belongs with. A file the target has is refused unless `replace`; folders a move empties go, and the window's toast offers Move back. `hide_files` (`rmm hide <mod> <paths> [--show]`, the panel's **Hide files…**, the plugin menu's **Hide the plugin**) moves files into the mod's `.rmm-hidden/` folder, which its file index leaves out, so they leave deploys, file conflicts and the plugin list (MO2's `.mohidden`; a hidden plugin is MO2's optional ESP). The mod's `rmm-mod.toml` lists them (`hidden`), the panel shows them with Show, and a reinstall or update hides them again. Each is one undo step: before it, the folders it changes are kept as hard links in `trash/.replaced/` (as a tool run's are), and undo and redo swap them back, the target's replaced copies included. Problems has an info finding (`overwrite_files`) while Overwrite holds files.

**Creation Club content.** `creation_club` (`rmm creations [--restore] --apply`, the Play menu's **Creation Club content…**) takes the plugins the game's `.ccc` file lists (`Skyrim.ccc`, `Fallout4.ccc`) that are in its Data folder, with their archives (`<name>.bsa`, `<name> - Textures.ba2`), out of Data into one mod each (`creation = true` in `rmm-mod.toml`), on and at the top of every profile, as MO2's Curation Club does: each can be turned off, and Purge or Play without mods leaves them all out. Deploy links them back. It isn't an undo step, since the files were the game's: undo keeps Creations in the list, switching to a profile without them adds them on at the top, and `--restore` purges, moves their files back into Data (those Data lacks) and takes the mods out of every profile, their folders to trash/. Plugins a mod already provides aren't taken.

**Reviewing mods** (`inspect.rs`, for an AI to judge what a mod does; `rmm scan`, `rmm read`, `rmm plugin-conflicts`):

- `scan_mod`: with a mod id, Windows Defender's command-line scanner checks the mod's folder (`MpCmdRun -Scan -ScanType 3 -DisableRemediation`, so nothing is quarantined; when another antivirus has replaced Defender it says so). Every file starting with `MZ` is read as a PE (the `object` crate): its imports are matched against capabilities (network, starting programs, registry writes, writing into other processes; keyboard or clipboard reads and encryption as info), packer section names (UPX, Themida, VMProtect…) are flagged, and its ASCII and UTF-16 strings are searched for shell commands, autostart paths, webhook and paste sites (warnings), URLs and addresses (info). A program with another extension (`.dds`) is a threat; scripts Windows runs (`.bat`, `.ps1`, `.vbs`…) are warnings; a DLL in `SKSE/Plugins` without `SKSEPlugin_Load` and DLLs under `root/` (loaded into the game by Windows) are noted. Verdict: threat, review or clean. Without an id every mod is triaged without Defender, listing only mods with native code or findings. These are leads, not proof.
- `read_mod_file`: text files as text (UTF-8, UTF-16 with BOM, or 8-bit), paged by line. Compiled Papyrus scripts are disassembled: Skyrim's (big-endian, 3.2) and Fallout 4's (little-endian, 3.9, with structs and its extra opcodes) give the script, variables, properties, states and each function's instructions. A test reads every `.pex` under `RMM_PEX_DIRS` and requires each to parse to its last byte (2,515 real scripts from Skyrim and Fallout 4 mods do). DLLs and EXEs come as machine, imports, exports, sections, signature presence and notable strings.
- `plugin_conflicts`: every enabled plugin outside the base game, DLC and Creation Club is read whole (esplugin), its record ids resolved against all plugins' headers, and each pair that shares records is listed with the count, the plugin loading later (whose version the game uses) and whether that one has the other as a master (a patch).
- `save_review` keeps a reviewer's conclusion with the mod, in `rmm-mod.toml`: a verdict (clean, suspicious or malicious), notes on what it does, what was checked and what it costs, and where it belongs in the order. It records a fingerprint of the mod's files (paths and sizes, plus the archive's sha256), so `mod_reviews`, `scan_mod` and the window's details panel show whether the files are still the ones reviewed. A reinstall or update marks the review out of date instead of dropping it. This is what spares the next AI the same checks (`rmm review`, `rmm reviews`). Not undoable, like notes.
- `plugin_records`: the records a plugin adds rather than changes (quests, NPCs, items, spells, cells, globals and so on by default), read straight from the file. Groups are walked, compressed records unpacked (zlib), and each record gives its editor id (`EDID`, what `coc`, `startquest`, `setstage` and `set` take), its name (`FULL`, unless the plugin is localized) and its form id in the current load order (full plugins count up from `00`, light ones share `FE`; none while the plugin is disabled), what `player.placeatme`, `player.additem` and `player.addspell` take. Unnamed exterior cells are counted but not listed (`rmm records`).

**History.** `history` (CLI `rmm history`; the window's History tab) lists the undoable changes newest first, each with what it did and when (the snapshot file's time), what Redo brings back (the next first), when this instance last deployed and started the game, and how many steps are kept (`history.limit`, 200 by default; older steps are dropped, and the window says so once the list is full). A run of moves of the same mods (`move X to 5`, then `move X to 6`, with nothing in between and nothing to redo) is one step that takes the newest label, so holding Ctrl+Down doesn't push older steps out. Besides undo and redo, `restore{n}` goes back to before history entry `n` (0 is the newest) in one step: it undoes every entry up to `n`, so redo can step forward again. A step that takes a mod off the list (an install undone, an uninstall redone) moves its folder to `trash/`, unless another profile lists it; a mod whose files were deleted with the trash leaves the list instead of coming back. The window previews what changes first, and the history and the preview leave out mods deleted with the trash. Long operations (install, import, deploy, lockfiles) report progress to the window.

**Profiles** each hold their own enabled mods, mod order, plugin order and undo history. Installed mods, `overwrite/`, tools and the LOOT userlist are shared, as in MO2 with its default settings. Install and uninstall change the active profile. Switching to another profile adds mods installed since it was last active at the end, disabled with their plugins, and drops mods that were uninstalled. A new profile is a copy of the active one (its own INIs too) or empty; an empty profile lists every installed mod, disabled, from its first switch (the window then turns the script extender's mod back on: `script_extender_mods` finds mods with its loader in `root/`). The game folder follows on the next deploy, which is incremental, so `switch_profile` returns that deploy as a dry run. Delete never removes the active profile and moves the folder to `profiles/.deleted/`. Profile operations are not in the undo history.

A profile can keep its own INI files and its own saves (MO2's two profile options; `set_profile_options`, `rmm profile options`, or the profile menu). Both take effect on a real deploy, which puts My Games in line with the active profile:

- **Own INIs:** `<game>.ini`, `<game>Prefs.ini` and `<game>Custom.ini` are copied from `profiles/<name>/ini/` into My Games. A profile's first deploy starts from the user's own INIs, which rmm keeps in `ini-backup/` meanwhile. Before the next deploy or a purge, the files in My Games go back to the profile they came from, so changes made in the game or its launcher stay with that profile. Deploying a profile without the option, or purging, puts the user's own INIs back and removes INIs the user didn't have. Renaming the profile carries this over; if it was deleted, its last changes are dropped.
- **Own saves:** `sLocalSavePath=Saves\<name>\` under `[General]` in the main INI, so the game saves into `Saves/<name>/` next to the usual folder. rmm remembers the line it replaced (or that there was none) and puts it back on the next deploy or a purge.

**New playthrough** (`new_playthrough`, `rmm profile playthrough`, the profile menu): a copy of the active profile with its own saves, made active, so a new character's saves stay apart from the others; the saves made so far stay with the profile they were made in. **Copy or move…** on the Saves tab (`transfer_saves`, `rmm saves --copy-to|--move-to <profile> <files>`) puts saves of the active profile into another profile's save folder, each with its `.skse`/`.f4se` co-save. A file of that name already there stops it before anything is done; two profiles without own saves share one folder, so that is refused too.

**INI tweaks** (MO2's): `.ini` files in a mod's `INI Tweaks` folder, each turned on per mod (`ini_tweaks` in `rmm-mod.toml`; the mod panel's checkboxes, `set_ini_tweak`, `rmm ini-tweak <mod> [file] [--off]`). An MO2 import keeps which were on. A real deploy writes the settings of the tweaks that are on, in mod order so a lower mod wins, into My Games: a key goes to `<game>Prefs.ini` if that file already has it, else to `<game>.ini`; a missing INI is skipped. The value each replaced is recorded and put back (a section rmm added goes again) on the next deploy or a purge, before the profile's own INIs are handled, so a tweak turned off comes out.

`ini-state.json` records what is in My Games, so an interrupted switch is finished by the next deploy or purge. The game must not be running (deploy and purge already refuse then): it writes its prefs on exit.

## Deployment

- **Default: incremental hard links plus a manifest, on both Windows and Linux.**
  - Each deploy diffs the desired state against `deploy.json` and only touches files that differ. The desired state comes from cached per-mod file indexes, so profile switches stay cheap. Vortex also diffs, but it walks every staging folder on each deploy and runs two deploys per profile switch (see `docs/internals/vortex.md`).
  - Launches cost nothing extra, unlike MO2's virtual filesystem.
  - It falls back to copying when the instance is on a different drive from the game.
- **Root files** (SKSE/F4SE loaders, ENB, ReShade) live in a mod's `root/` folder and are deployed to the game root. This replaces MO2's Root Builder.
- **overwrite/ is the top layer** (MO2's model). It sits above every mod in conflicts and deploys, and is re-scanned on every deploy because tools keep adding to it.
- **External changes are detected by file identity.** rmm compares the NTFS file id or inode of the deployed link with its source.
  - An edit made in place through the link changes the mod file with it, so rmm can't tell it apart and counts it as its own. That is acceptable for the game and for deliberate edits, but tools rewrite files this way too (BodySlide, Nemesis, BethINI; see `docs/internals/tools/`). Tool runs therefore swap the links they would write through for copies (see "Tools").
  - A replaced file is detected even if its size and mtime match.
  - Replaced files are captured to `overwrite/` before anything else, so they win in the same deploy.
  - `deploy.json` keeps each link's file id and the id of the mod folder it came from. A link rmm made to a file its mod no longer has (reinstalled, or uninstalled) is recognised as rmm's even after the trash is emptied, and is relinked or removed rather than captured.
  - Copies fall back to the size and mtime recorded at deploy.
  - Deploys, Play and dry runs (the window's Deploy count, the health check) list the game folder once; on Windows that listing carries every file's id, so no file is opened. Mod folders are immutable (reinstalls and tool reruns replace them whole), so a link that is still the file rmm linked, from the same mod folder, needs nothing more. Files in `overwrite/` (changed in place), copies, and anything that fails this get the full check. On a 1,200-mod list with 127,765 deployed files, a deploy with nothing to do takes 2.5–3 s in release, against 38.9 s for opening every file. The first deploy after upgrading from a `deploy.json` without ids does the full check once (25 s there) and records them. Dry runs take no lock.
  - A deploy that fails part-way still saves `deploy.json` with every file it changed, and records a file before linking it, so the next deploy finishes the job instead of backing up rmm's own links as the user's files.
  - Backups and their restores fall back to copy and delete when the instance is on another drive.
- **Script-extender plugin settings are copies.** `.ini`, `.json`, `.toml` and `.yaml` files under `Data/SKSE/Plugins` and `Data/F4SE/Plugins` are deployed as copies, not links. Plugins such as CrashLogger and NGIO rewrite theirs every time the game starts. With a link, that rewrite would change the mod's own file; with a copy it shows up as an external change and goes to `overwrite/`. Copies, these and cross-drive ones, keep their source's mtime on every platform, so a copy whose mod file has changed since the deploy is copied again.
- **Files written during play.** `launch_game` notes which Data files rmm doesn't manage. The next deploy (or purge) moves files that appeared since then into `overwrite/` and links them back, so MCM settings, crash logs and caches the game creates are managed like everything else (MO2 sends them to overwrite too). A game started from Steam rather than `launch_game` leaves its new files unmanaged.
- **A folder rmm made** that a mod now replaces with a file is removed, not backed up.
- **Tested against Vortex's planner.** Vortex's next deploy planner (`packages/mod-pipeline`) is a decision table over disk × previous deploy × current profile, with a JSON fixture per row. `tests/flow.rs::vortex_planner_rows` sets up each row that applies to rmm and checks the result. rmm differs on purpose in two places: a file changed outside rmm goes to `overwrite/` and keeps winning, where Vortex backs it up and replaces it; and backups are restored on purge, where Vortex never restores them. The hash and symlink rows don't apply.
- **Refusals.** rmm refuses to deploy in three cases:
  - the game is running (Windows: its .exe can't be opened for writing; Linux: `/proc` lists it);
  - the game folder holds `vortex.deployment*.json`;
  - `deploy.json` is missing while `.rmm-owner` says the folder is still deployed.
- **Purge without a manifest** removes every game file that is a hard link to a file in `mods/`, `trash/` or `overwrite/`, then restores `backup/`. Cross-drive copies can't be identified this way and stay.
- **Letter case on Linux.** Paths are matched without regard to case, as on Windows. A deployed file takes the spelling of the mod that wins it, and each folder on its way is matched to the spelling already on disk, so `Textures/` from one mod and `textures/` from another end up in one folder.
- **VFS mode (Linux):** `rmm vfs` mounts a FUSE filesystem over the game's `Data` folder until Ctrl+C (or SIGTERM or SIGHUP), for users who want a Data folder that is never touched.
  - The view is vanilla Data with the enabled mods and `overwrite/` on top: the same winners a deploy would link, matched without regard to case. Root files and `plugins.txt` deploy as usual.
  - Writes go to `overwrite/`. A file is copied there before its first change, so mods and vanilla files never change. Renaming a folder isn't supported (programs fall back to copying).
  - The view is fixed when it mounts: remount after changing the profile. Deleting a file hides it until the next mount; only files in `overwrite/` are really deleted.
  - Deploy, purge and launch refuse while it is mounted (`vfs.pid` in the instance), so start the game from Steam.

| | Skyrim SE/AE | Fallout 4 |
|---|---|---|
| Steam app id | 489830 | 377160 |
| Detection | Windows registry `Bethesda Softworks\Skyrim Special Edition`, then Steam `libraryfolders.vdf` | same, key `Fallout4` |
| Local dir (Windows) | `%LOCALAPPDATA%\Skyrim Special Edition`, with ` GOG` / ` EPIC` / ` MS` for other stores | `%LOCALAPPDATA%\Fallout4`, or `Fallout4 MS` / `Fallout4 EPIC` |
| Local dir (Proton) | `<lib>/steamapps/compatdata/489830/pfx/drive_c/users/steamuser/AppData/Local/Skyrim Special Edition` | `…/377160/…/Fallout4` |
| INIs | `Documents\My Games\<local folder name>` (Proton: `…/steamuser/Documents/My Games/…`); `ini_path` in `instance.toml` overrides | same |
| Script extender | `skse64_loader.exe` | `f4se_loader.exe` |

The store is recognised by a file only that store installs: `Galaxy64.dll` (GOG), `EOSSDK-Win64-Shipping.dll` (Epic) or `appxmanifest.xml` (MS). This is the same rule as libloadorder and Vortex. Registry and Steam detection only find Steam installs. **Auto search** (`rmm detect --search`, the welcome screen, and the MO2 import's list, which keeps the instances for the instance's game) looks through every fixed and removable drive, six folders deep, for a game's exe beside a Data folder and for MO2 instances (`ModOrganizer.ini`, portable ones included). It skips Windows, hidden and system folders and links, and doesn't look inside what it finds. Otherwise, pass `--game-path`.

Libraries: `libloadorder` (load order, plugins.txt), `libloot` (sorting, masterlists, messages), `esplugin` (headers, masters, ESL eligibility), `zip` / `sevenz-rust2` (archives; RAR goes through libarchive's bsdtar, which Windows ships as `System32	ar.exe`). Licence: **GPL-3.0**, because these libraries require it.

## AI integration (MCP)

`rmm mcp --instance <dir>` runs a stdio MCP server. Its instructions are `crates/rmm/src/ai-guide.md`, compiled in: what every AI working on the instance is told, given to apps as the server's instructions. It keeps the AI on the user's request (what is in scope, answering asides briefly, listing what it noticed as suggestions, stopping after the same failure twice, what to ask first, and what done means), then how rmm works.

`rmm mcp --http 127.0.0.1:47823` serves the same tools over streamable HTTP at `/mcp`, and the window's **MCP** tab does the same while the window is open, so changes the AI makes appear live in the UI. Every tool returns structured JSON. Mutations go through the same core functions and the same history, so **everything the AI does can be undone**.

The HTTP server is a subset of the streamable HTTP transport (MCP 2025-06-18): each POST carries one JSON-RPC message and gets a JSON answer, or 202 for notifications. There is no SSE stream, so GET gets 405, which the spec allows. `initialize` starts a session (`Mcp-Session-Id`) and DELETE ends it. It listens on the loopback address only. Every request needs `Authorization: Bearer <token>` (random, made on first use and kept in `rmm/mcp-token` in the user's config folder so client settings survive restarts; the CLI prints it, the window shows it), and requests with a browser's `Origin` or a Host other than the loopback address are refused, against DNS rebinding.

**The mod team.** The server also offers four prompts, which clients show as commands. Each one is a role that the user's own AI plays, or hands to a sub-agent when the client can start them; rmm runs no model itself.

- `find_mods{request}`, the researcher: turns a description, images or "works with <mod>" into Nexus searches; reads each candidate's page and requirements against the list; and returns a short list scored 0 to 100. The user picks.
- `install_safely{what}`, the installer: downloads the pick and its missing requirements, keeps it disabled until reviewed, and reuses a current saved review or scans the mod and reads its DLLs and scripts. It saves the verdict, places the mod by file and record conflicts and LOOT, then deploys.

- `mod_team{request}`, the lead: runs the other three, has the user pick, and guides the tester (where to go, what to fight, which quest stage) until each mechanic works or clearly fails.

Video can't be watched by the client, so the researcher asks for screenshots or a description instead.

### Sessions of AI apps

The stdio server and each HTTP session record their client's calls (`Rmm::recorded`, unless `mcp.record_sessions` is off), in `ai/chats/<id>.json` in the instance (`crates/rmm/src/chats.rs`). Every `tools/call` passes through one `call_tool` that appends the call and its answer (cut to 2,000 bytes) to a chat with provider `mcp` and the client's name from its `initialize` (`title`, else `name`) as the model, and saves it. The chat is made on the first call and only inside an instance; writing it never fails a call. MCP doesn't carry the conversation to the server, so the instructions ask an app to call `save_chat_note` when a task ends: the note is added as the AI's words and the first one becomes the title. `read_chat` shows it to any later session. Chats left by rmm's former built-in AI still list and read.

### Workspace files (`crates/rmm-core/src/workspace.rs`)

The AI's file tools reach three roots by workspace path: `mods/<mod id>/<path>`, `overwrite/<path>`, and `ini/<file>` (the `.ini` files in the INI folder the game reads now; with a profile's own INIs deployed those are the profile's, and a later deploy copies them back to it). Paths with `..`, drive letters or anything outside these roots are refused.

- **Reading** gives text with a hash of the bytes. UTF-8 (with or without a BOM), UTF-16 with a BOM, and 8-bit text are read; compiled Papyrus scripts come disassembled and DLLs as their summary, read-only; other binaries can't be opened. Files over 8 MB are refused.
- **Writing** keeps the file's encoding (8-bit text refuses characters it can't hold). A write with a hash refuses when the file changed since (the window then asks before saving over it). The old bytes go to `edits/<n>.bak` and `edits/log.json` records the edit: number, path, time, who (you, AI, revert), whether the file was made, lines before and after. Mod files are written in place, so through deploy's hard links the game sees the change at once and deploy still counts the file as its own; INIs apply when the game next starts. New files can be made in a mod's folder or `overwrite/`, not in the INI folder.
- **The AI's edits** replace text found exactly once (zero or several matches fail, so the edit lands where meant) or write a whole file. In the window they come as a diff for approval.
- **Revert** puts a file back as it was before edit n; a file the edit made is removed (its last content kept in `edits/`). A revert is an edit, so it can be reverted too.

## FOMOD

`fomod/ModuleConfig.xml` installers (schema 5.0 and earlier) run headless in `rmm-core::fomod`. The rules follow MO2's evaluator:
- Steps, groups and options are sorted by name unless `order="Explicit"`.
- A flag takes the value from the most recent visible step that sets it. An unset flag only matches an empty value.
- Default picks: Required and Recommended options; a group that must have a selection gets its first usable option.
- Files come from required files, then conditional installs, then the selected options. A stable sort by `priority` decides overlaps, with the later entry winning ties.
- File conditions are checked against the instance: winning mod files and Data. A plugin the profile has disabled counts as inactive.
- Script-extender conditions check that the loader is present. Game and FOMM version conditions count as met.
- Paths that climb out with `..` are skipped with a warning.

**BAIN packages** (Wrye Bash) are read as a FOMOD with one step, "Sub-packages", where any can be picked. Detection follows MO2: at least two top-level folders, each Data-like (Data folders, a `data` folder, or plugins and BSAs), with `fomod`, `omod conversion data`, `images`, `screenshots`, `docs` and `--` folders ignored. Each pick installs its folder to Data, a later one winning; `00…` packages are Recommended, so ticked by default. `wizard.txt` isn't run (a warning says so) and `package.txt` isn't shown. Since it is a FOMOD, choices, reinstall and MCP work as above.

**C# script installers** (`fomod/script.cs`, old FOMM mods) run in `rmm-core::csharp`, Windows only. The script is compiled with .NET Framework 4's `csc.exe` against a stand-in for FOMM's `BaseScript` and run by a small host in a sandboxed AppDomain that may only execute and show windows: it can't read files, the registry or the network itself. Its calls go through a bridge that answers from the mod's files, the game's Data, the instance's winning files and plugins, and records what to install: `CopyDataFile`/`InstallFileFromFomod` copies, `GenerateDataFile` files, plugin activation and INI edits. The script's own dialogs (`Select`, `MessageBox`) are real windows. INI edits become the mod's `INI Tweaks/Installer script.ini`, turned on. A script that reaches outside the mod fails with a message saying to install the folder by hand. A script is only run with consent: the window asks first ("Run … installer?"), the CLI needs `--run-script` on `install`, `reinstall` and `update`. MCP, the built-in AI, collections, lockfiles and imports never run one.

`fomod_options` returns every visible step and the full resolved choices. Choices find their step and group by name; steps or groups sharing a name (some installers name none) are matched in order, the second "" to the second "". An AI edits the choices and calls it again (choices can reveal later steps), then passes them to `install_mod`. Choices use Vortex's `installerChoices` shape and are stored in `rmm-mod.toml`. Choices for a step the installer doesn't show with the other choices aren't used, and the walk says so in its warnings. An archive is unpacked once into `.staging/preview` and reused by the install that follows.

## Tools

A tool is any program rmm launches against the deployed setup: xEdit, BodySlide, Synthesis, or anything else. Each one is stored in `tools.toml` under a stable id. A tool has an exe, an argument template, default vars, `rewrites` (Data-relative globs of files it rewrites in place) and the name of its generated mod. Two optional fields cover tools that keep state:
- `settings`: a JSON file (relative to the exe) and dotted keys rmm sets in it before each run, for tools that read their paths only from there. Placeholders work in string values. After the run those keys go back to their old values (or are removed if they weren't there); everything else in the file, including what the tool saved during the run, stays. A file rmm made that holds nothing once its keys are out is removed. The settings file is never part of the output, even for a tool installed as a mod and run from Data.
- `keep`: globs of files copied from the previous output into `{output}` before the run, for state the tool reads back from its output folder.

The window's **Add a tool** takes all of these: its **More** section has keep, rewrites, the program to wait for (`wait_for`), the settings file and its `key = value` lines (values are JSON or text). Fields left empty keep the preset's own. `remove_tool` (MCP, the Tools tab's Remove) takes a tool out of `tools.toml`; its generated mod and state folder stay.

Presets fill in these fields; the exe always comes from the user. They come from reading each tool's source (`docs/internals/tools/`):

| `xedit-qac` | both | yes | QuickAutoClean of `{plugin}` into a "Cleaned {plugin}" mod |
| `xlodgen` | both | no | xEdit in `-lodgen` mode with `-o:{output}\`; without `-o` it writes to the game folder |

`run_tool` (CLI `rmm run <id>`) previews with `dry_run`. A real run goes through these steps:
1. Disable the tool's previous generated mod (identified by `source = "tool:<id>"` and its name), then deploy, so the tool sees the current setup without its old output.
2. Swap deployed hard links matching `rewrites` for copies, and keep copies of matching vanilla files.
3. Snapshot the game folder (size and mtime of every file, read from the file rather than the directory listing).
4. Run the tool. The working directory is the exe's folder, stdout and stderr go to `tools/<id>/last-run.log`, and an optional timeout applies. A tool with `wait_for` (a program relative to the game folder) also waits for that program: launchers such as `skse64_loader.exe` and `ckpe_loader.exe` start the real program and exit. Grass precaching, for instance, runs the game through SKSE with `wait_for = "SkyrimSE.exe"`.
5. Diff the game folder. Data files go to the generated mod's top level, files in the game root to its `root/`. Files go in as follows:
   - **The `{output}` folder:** moved in.
   - **New files:** moved in.
   - **Changed files rmm deployed:** moved in.
   - **Changed vanilla files:** the new version goes in, and the kept original goes back so deploy can back it up.
   - **A changed file still linked to its mod:** the tool wrote through a link not covered by `rewrites`. It is reported in `modified_in_place`, because that mod's file is now changed for good.
   - **Untouched swapped copies:** removed, so the next deploy relinks them.
6. If anything was captured, the new generated mod takes the previous one's place in the order (or goes last) with its plugins enabled. The previous one goes to `trash/`, so undo brings it back. Then rmm deploys.
7. If the run added plugins the profile didn't list and a LOOT masterlist is cached (the user sorts with LOOT), rmm sorts and rewrites plugins.txt. The first sort and its download stay the user's call.

Before step 3, kept files are copied into `{output}` and the settings file is edited. A run whose output holds only kept files counts as capturing nothing.

Exit codes are reported but not trusted, because BodySlide and Pandora return 0 on failure. A run that captures nothing re-enables the previous output.

**Editing in place** (`edit_in_place`, `--edit-in-place`, the Add a tool dialog's "Save edits into the mods they change"; the `xedit` preset's default) suits patching sessions, like MO2's "create files in mod":
- Nothing is disabled in step 1, so the tool sees its earlier output.
- A changed file rmm deployed goes back into the mod it came from (the one that won it), replacing that mod's file. It's listed in `into_mods`.
- New files, changed vanilla files and `{output}` go into the output mod: an installed mod whose id or name is `output_mod` (any mod, such as the user's own patch mod), added to rather than replaced. With no such mod, a new one by that name is made at the end of the list. Only plugins new to the profile are enabled.
- Before rmm changes a mod, it keeps the mod's files as they are in `trash/.replaced/<id>-<n>` as hard links, so the copy costs no space. The run is one undo step that swaps those folders back (redo swaps them again), as an update in place does.
- A file the tool wrote through a link not covered by `rewrites` is already changed in its mod; undo can't bring its old contents back. xEdit saves by writing a new file and renaming it over the plugin, so this doesn't happen with it.

**Out-of-date output.** A run of a whole-setup tool keeps in its generated mod's `rmm-mod.toml` (`built_from`) what the tool read. It counts only the files that tool reads: behaviour files for Pandora, BodySlide's sliders, plugins and LOD files for DynDOLOD and xLODGen, and everything for Synthesis. That is one fingerprint per enabled mod (its file list, plus the archive or Nexus file it came from) and one for the enabled plugins: their order, size and mtime, so an xEdit edit under the same name counts. `built_from` keeps which of these it read (`reads`). Output with no `built_from` (every imported one), or one taken under different rules, is unknown: Problems gives an info finding, not a warning, and the Tools tab shows each tool's output as Up to date, Out of date or Unknown, with its last run. Generated output is left out, so outputs don't make each other stale. The whole-setup tools are the `CHAIN` presets: xLODGen, TexGen, DynDOLOD, Pandora, BodySlide, Synthesis and PGPatcher, matched by tool id or by the preset's name. When the setup has changed since (mods added, removed, turned off or updated, or the load order changed), Problems warns (`stale_output`) and names what changed. `rebuild_outputs` (`rmm rebuild [--apply]`, **Rebuild outputs…** on the Tools tab and in Problems) runs those tools again in chain order, each as a run of its own. It runs the ones whose output is out of date, or was made before rmm kept track. It stops at the first failure, since later tools read its output. Tools with no output in the profile are left alone. Installs already go in before the trailing generated output, so output stays last. A tool rerun with no change to the mods doesn't mark the outputs made after it as stale; changes to a mod's files under the same names (an update from a folder) aren't seen.

The report is also saved to `tools/<id>/last-run.json`. Over MCP, `run_tool{background: true}` returns at once and `tool_job` reports the run (running, done with the report, or failed). While a background run owns the game folder, the server refuses changes to the setup; reads and dry runs still work.

**Linux.** A Windows tool runs through Proton in the game's prefix, the way Steam runs the game: `proton run <exe>`, with `STEAM_COMPAT_DATA_PATH` set to the game's `compatdata` folder. The Proton build and the Steam folder come from the prefix's `config_info`, which Proton rewrites on every run, so the game has to have been started once from Steam. Path placeholders become Wine paths on drive `Z:`.

## Launch

`launch_game` (CLI `rmm launch`) previews with `dry_run`. A real launch:
1. Deploys. This refuses while the game is running.
2. Reads the game's version from its exe's version resource (`VS_FIXEDFILEINFO`).
3. If the script extender's loader is in the game folder, finds its runtime DLL, which names the game version it was built for (`skse64_1_6_1170.dll`, `f4se_1_10_163.dll`). A loader without a DLL for this version is refused with both versions named; the loader itself would only show an error box. Without a loader it starts the game exe, with a warning if script extender plugins are deployed.
4. Notes the Data files rmm doesn't manage (see "Deployment": files written during play).
5. Starts the loader or the game from the game folder and returns its process id without waiting. On Linux it starts through Proton like a tool (see "Tools"); Steam has to be running.
6. Writes the game version to `game-version.txt` in the instance.

**Without mods.** `launch_game{without_mods}` (`rmm launch --without-mods`, Play's menu, and the dialog Play shows when the script extender doesn't match the game) purges instead of deploying and starts the game's own exe; it isn't noted as a Play, and the next Play deploys the mods again. It is for a game update that broke the script extender.

**Shortcuts.** `desktop_shortcut{profile, dry_run}` (`rmm shortcut [<profile>] [--dir] --apply`, the profile menu's **Desktop shortcut…**) writes `<game> - <profile>.lnk` to the Desktop (Windows' known folder, so a OneDrive Desktop too), with the game's icon, as MO2's shortcuts do. The window shows what it would make first (a dry run) and writes it only on **Make the shortcut**. It runs the rmm command line next to the app with `-i <instance> launch --profile <p> --apply --pause`: `launch --profile` switches to the profile first (a dry run only looks at it), and `--pause` keeps the console open on an error until Enter, since a shortcut's window closes with rmm. The window shows the program and arguments for Steam's **Add a Non-Steam Game**, and notes that the game's own Steam entry skips the script extender and undeployed changes. PowerShell's `WScript.Shell` writes the `.lnk`, its values passed through the environment.

**Steam's updates.** `steam_updates{hold}` (`rmm steam-updates --hold/--release`, Play's menu) makes the game's Steam manifest (`steamapps/appmanifest_<app id>.acf`, beside the `common` folder the game is in) read-only so Steam can't update the game, after keeping a copy in `ini-backup/`, or writable again; without `hold` it says which it is. Problems has an info finding while it's held. Releasing asks first in the window, since Steam may update right away and undo a downgraded game.

**Game updates.** A game patch breaks the script extender, Address Library and many of its plugins, which are each made for one game version. The health check (and Play's warnings) says so in three findings:
- `game_updated`: the exe's version differs from `game-version.txt`, the version at the last Play. It goes away at the next Play.
- `address_library_mismatch`: Address Library is installed but has no file for this version. Its files in `Data/SKSE/Plugins` or `Data/F4SE/Plugins` name the version they are for (`versionlib-1-6-1170-0.bin`, `version-1-5-97-0.bin`, `version-1-10-163-0.bin`; `.csv` in VR). The finding names the newest versions it covers and links its Nexus page.
- `script_extender_plugin`: a plugin DLL from one of the setup's mods didn't load in the last run, with the log's reason (an Address Library or runtime mismatch, a missing dependency) or, when the log ends after checking it, that the game may have closed while loading it. A mod installed or updated after that run isn't blamed.

`read_script_extender_log` (CLI `rmm script-extender-log`, the Problems tab's **Script extender log…**) reads `skse64.log` or `f4se.log` from the My Games folder: each plugin DLL the script extender checked, loaded or not and why, with its mod. DLLs it reports as not being plugins (Crash Logger's `msdia140.dll`) are left out.

## Nexus Mods

API v1, with `curl`. The user signs in with the window's account button ("Sign in to Nexus", which opens the API Keys page) or `rmm nexus login`, which reads the key from stdin: they paste their personal API key. The button then shows the account and Premium status, and offers Sign out and "Open Nexus links with rmm" (the handler below). The window also offers the handler right after signing in, and says which program opens the links now (read from `HKCR
xm`). rmm checks it with Nexus, then saves it to `rmm/nexus.key` in the user's config folder (`%APPDATA%` on Windows; only the user can read it on Linux). `RMM_NEXUS_KEY` overrides it. The key never goes into an instance, a lockfile or a command line: curl gets it on stdin.

**Single sign-on** (`rmm nexus login --sso`, or "Sign in on nexusmods.com" in the window's key dialog) gets the same key without copying it. It follows Nexus's SSO protocol 2: rmm opens a websocket to `wss://sso.nexusmods.com`, sends a random id, opens `nexusmods.com/sso?id=…&application=…` in the browser once Nexus answers with a connection token, pings every 30 seconds, and receives the API key when the user approves rmm (or gives up after 10 minutes). The key is then checked and saved like a pasted one. The application name comes from Nexus staff when they register rmm. Until then `SSO_APP` in `nexus.rs` is empty and single sign-on is off (the window shows only the key field), unless `RMM_NEXUS_APP` sets a name. The websocket is a small client on rustls, which the build already had. A test plays a fake Nexus (handshake, masked frames, ping and pong, the key), and an ignored test checks the TLS handshake and first answer against the real service.

- **Downloads.** `rmm nexus register-handler` (or the window's "Open Nexus links with rmm") makes `nxm://` links, the website's "Mod manager download" buttons, run `rmm-app -i <instance> nxm <link>` (`rmm` where the window program isn't installed; a handler set up for `rmm.exe` is moved to `rmm-app.exe` when the window next opens the instance). The window program is a windowed one, so no console opens for a click. It leaves each link as a file in `.nxm-inbox/` and quits when a window has the instance open (the window holds `.window-lock` in the instance locked while it is open), or becomes that window. `rmm nxm` does the same, starting the window instead. The window comes to the front, downloads the files one at a time and installs each like a dropped file, so FOMOD installers show their options, a newer version of an installed mod is offered as an update, and a failed download stays in Problems. Links clicked while no window is open start one window. Without the window program beside `rmm`, `rmm nxm` downloads and installs the file itself with the installer's defaults, as `rmm nexus install` does. Registering the handler changes the system's handler (`HKCU\Software\Classes\nxm` on Windows, `xdg-mime` on Linux), so it is the user's call. Premium accounts can also download by a mod page link, a mod id (its newest main file) or `<mod id>/<file id>` (`rmm nexus install`, `install_from_nexus`, the window's "From Nexus…"); for a free account rmm says to use the website's button instead of letting Nexus refuse. The file is saved under its name on Nexus (newer uploads' download links end in an id), and one already in downloads with that name and size isn't downloaded again. Archives are opened by their first bytes, so a ZIP named `.7z` still installs. The mod remembers its game, mod id, file id and version in `rmm-mod.toml`. Downloads go through `<file>.part`, which a failed or stopped download leaves: the next try asks curl to carry on from it (`-C -`; a server that can't send part of a file gets one fresh try), a part larger than the file is dropped, and the result must have the size Nexus gives. The window queues links (the website's buttons and From Nexus…) and keeps failed ones on the Downloads tab with Retry.
- **Identifying downloads.** `identify_downloads` (`rmm nexus identify`, the Downloads tab's Identify on Nexus) looks files in `downloads/` up by their MD5 (`md5_search`; certutil computes it on Windows), the given ones or every one not identified yet, and keeps what it finds in `downloads/.nexus.json` with what rmm downloaded itself. Installing from such a file records its Nexus ids and name, and installed mods made from one that have no Nexus ids get them, so update checks see them. A refused key or a used-up request limit stops the rest.
- **Collections** (`rmm nexus collection <link>`) install a collection's revision (the newest unless `--revision` names one) into the active profile, or with `--profile <name>` into a new empty profile that becomes the active one, as Vortex does: the mods already installed are in it, turned off, and the script extender stays on, so the user's own profile stays as it was. The window's From Nexus… takes a collection link (a preview, then optional mods and a new profile, on by default) and MCP has `install_collection{new_profile, dry_run}`. Its `collectionRevision` (GraphQL) gives the bundle's link; the bundle (`collection-<slug>-<revision>.7z` in downloads) holds `collection.json`, the format Vortex writes. Each required mod (and with `--optional` the optional ones) is downloaded from its Nexus file and installed phase by phase with the curator's FOMOD choices, and records its Nexus ids; one already installed from the same file is kept and turned on, so a second run adds only what is missing, and a mod that fails is listed and the rest go on. A mod the collection gives Vortex's `dinput` or `enb` type, which Vortex deploys to the game folder, has what isn't Data content (the Data folders rmm knows, plugins and archives, a plugin's own INI) moved into `root/`; Data content stays in Data, where it works, though Vortex would put it in the game folder too. The mod remembers this (`game_folder` in `rmm-mod.toml`), so a reinstall or update places it the same way. The curator's instructions become the mod's note. `modRules` become mod rules (A before B is B's *after A*, conflicts are *incompatible*), matched by archive hash, logical file name or archive name, then the mods are sorted by them; the plugin list sets which plugins are on, and LOOT sorts them (`--no-sort`, MCP `sort: false`, leaves that to a sort whose dry run shows what moves; the window does so, showing LOOT's preview with Cancel after the install or update, so a hand-placed plugin never moves unseen). The collection's tools become rmm tools (rmm's preset when it has one), leaving out the game and its script extender. Without `--apply` it downloads only the bundle and says what it would install, how much is left to download and which game version the collection was made for.
- **Collections on free accounts.** Nexus lets free accounts download only through the website, so the report's `to_download` lists the files that aren't in `downloads/` yet, each with its download page (`mods/<id>?tab=files&file_id=<id>&nmm=1`), and the install refuses until they're all there. The window opens those pages 3 at a time and shows how many are left (Open the next ones, Pause, Stop). nxm links that match a waiting file by mod and file id are downloaded, not installed, and once all are in, the install runs from `downloads/` as on Premium.
- **Endorse and track** (`rmm nexus endorse <id> [--abstain]`, `rmm nexus track <id> [--untrack]`, `rmm nexus account`; the mod panel's "Your Nexus account" and the right-click menu; not over MCP, since they act publicly on the account). The account's endorsements and tracked mods for the game are kept in `rmm/nexus-account.json` beside the key, read at the window's start, and show as the Endorsed and Tracked filters.
- **Collection updates.** The profile keeps the collection it was installed from (`[collection]` in `profile.toml`: slug, name, revision, whether optional mods came, its mods by id and its plugin list), so installing another revision there, with its link or with none (`rmm nexus collection --apply`, `install_collection` without `link`), is an update (`update_from` in the report). A mod of the old revision that the new one has a newer file of (the same Nexus mod, by name first) is updated in place with the curator's choices, keeping its place, rules, notes and enabled state; when another profile has the old one on (mod folders are shared), the new file goes in as a new mod just after it and the old one is turned off here. Mods the revision dropped are turned off, not uninstalled (`turned_off`). The user's own mods (`yours`), the collection's mods they turned off (`kept_off`) and plugins they turned on or off stay as they are: only plugins whose state the curator changed between revisions are set, and only mods that are off are turned on, since turning a mod on turns on its plugins. For a collection installed before profiles kept this, the earlier revision comes from its bundle in the downloads, counting the turned-on mods from its files. The window's Check for updates also asks for the collection's newest revision and offers Update…, which previews the update before applying it; each step is in the undo history.
- **Search** (`search_nexus`, `rmm nexus search`) and **mod pages** (`nexus_mod_info`, `rmm nexus info`) use Nexus's GraphQL API (v2), which answers without a key; the saved key is sent when there is one. Search matches words in names and descriptions (stemmed) within the instance's game, with a category (checked against `nexus-categories.json` for its exact name), a sort, paging and adult mods left out unless asked. A page comes with its description as plain text (BBCode removed, link addresses kept), tags, the mods and DLC it requires, and the mods that require it, which are its patches and add-ons. Each mod is marked with the installed mod that has its Nexus id. A page needs the game's Nexus number first (`game(domainName)`), since a list query for one mod with its requirements costs more than Nexus allows.
- **Update checks** (`check_mod_updates`, `rmm nexus updates`, "Check for updates" in the window, which marks mods with an Update tag) follow each file's `file_updates` chain from old file to new file, falling back to the newest main file's version. A mod whose page Nexus no longer has or hides (a 403 or 404 for its files: removed, hidden, a wrong id) is listed under `unavailable` and skipped, and the check goes on; a refused key, the request limit or no connection stops it. The window names those mods under the list or in its toast. Nexus allows about 100 requests an hour once the daily burst is spent, so a check first asks which mods changed in the last month and only re-reads those, plus mods not checked for 30 days. Answers are cached in `nexus-cache.json`, and what the check found in `nexus-updates.json`, so the tags come back with the window; a tag goes once the new file is installed. In the window, the row's Update tag, the panel's **Update**, the mod menu's **Update from Nexus** and the update list's **Update** download the new file (Premium) and update the mod in place, with the FOMOD choices it was installed with. The update list's **Update all** does every row not skipped, held or already queued, one mod after another: the GitHub ones, then the Nexus ones through the download queue (Premium; a free account's Update all takes only the GitHub ones, and with nothing but Nexus updates it has no Update all). An update whose FOMOD choices no longer fit, or whose files were edited in rmm, still asks as it reaches that mod. A free account gets the mod's Files tab instead, where "Mod manager download" brings the file back as an update. **What's new** shows the mod's Nexus changelog for the versions after the installed one (`nexus_changelog`, newest first).
- **Holding updates back** (`hold_updates`, `rmm nexus hold`, the mod panel's Updates section and the update list's Skip and Hold buttons): *pin* keeps a mod at its version, *skip* passes over the newer file the last check found (a later one is offered again), *release* undoes both. Held updates are left out of the check's results, the Update tags and the "Update available" chip; pinned mods show a Held tag. Holds live in the mod's `rmm-mod.toml`, like notes, so they aren't in the undo history. The mod list's Version column (off by default) shows each Nexus mod's installed version.
- **Requirements.** An install from Nexus (`install_from_nexus`, an nxm link, the window's From Nexus…), any install or update in the window of a mod with a known Nexus id (from the download's record or its file name, so the Downloads tab and dropped files too; no key needed), and every mod an update check re-reads, or has no requirements for yet, has its page's requirements read and kept in `nexus-requirements.json`. The health check's `nexus_requirement` finding names, for each enabled mod, the required mods that aren't installed or are disabled, with each one's page. A mod is matched by its recorded Nexus id, the id in its archive's name, or its name, and a stand-in counts too (on Skyrim SE, Pandora for Nemesis and FNIS, Nemesis for FNIS). A requirement whose author's note waives it is skipped: the note calls it optional, not required or "if you want", or limits it to other game versions ("older than 1.6.1130", "1.6.640+", "1.5.97 or older", "on 1.5", also read in the requirement's name, as in "… for Skyrim 1.5"). Only numbers the game's own versions have had count (1.5 to 1.7 for Skyrim SE, 1.10 and 1.11 for Fallout 4), so a mod's version number isn't taken for the game's. A required script extender (SKSE64, F4SE, linking to silverlock.org) counts when its loader is in the game folder or an enabled mod. Downloads from other sites aren't checked, and nothing is ever blocked: the finding says to ignore it when the mod comes another way. A DLC the page requires (`dlcRequirements`) counts when its master is in the game's Data folder (Dawnguard, HearthFires, Dragonborn, the Fallout 4 DLC); others, such as Creation Club bundles, aren't checked. `missing_requirements` (`rmm nexus requirements`) lists the same as data: each requirement, the mod that needs it, its Nexus id and page, the installed mod that's off, and whether it's a DLC. `rmm nexus requirements --install` (Premium) and the Problems tab's Install what's missing… install each one on Nexus (its newest main file, installer defaults) and turn on the ones that are off; a free account gets their Files tabs opened (up to 10 at a time). The script extender, DLC and other sites' downloads are left to the user, named in the dialog.

## Other sites (`crates/rmm-core/src/web.rs`)

- **Links.** `rmm install <link>` (`--file` picks one of several files), `install_from_link{url, file, dry_run}` and the window's "From a link…" download a mod from a link and install it like a dropped file. `rmm link show <url>` (the dry run) says what a link is: its site, the mod's name and the files to choose from.
  - **GitHub:** a repository (its latest release), a release's page (`/releases/tag/<tag>`) or a file's link. Its `.zip`, `.7z` and `.rar` files are offered, read from the public API, or from the release's web pages once the API's hourly limit for requests without an account (60) is used up.
  - **ModDB:** a download page (`/<kind>/<mod>/downloads/<file>`) or a mod page, whose downloads are offered. The file comes from the first mirror; the mod's name from the page's title.
  - **Any other link to an archive** downloads as it is.
  - **Sites that need the user's sign-in** (LoversLab, AFK Mods, Patreon) and pages that aren't files are downloaded in the user's browser. The window opens the page and lists archives that finish in the Downloads folder from then on (or earlier ones), leaving out ones a browser is still writing. The one the user picks moves into rmm's downloads folder, recorded with the page, and installs. The CLI and MCP say to download it and install the file. rmm never handles the user's passwords, cookies or sessions, and never gets past a site's sign-in or bot checks.
  - Nexus links given here go to the Nexus route.
- **Recording.** Each file is recorded in `downloads/.web.json` (file name to page, release tag and file name), and an install or update from it stores that as `web` in `rmm-mod.toml`. The mod panel links the page, and the Downloads list shows it. A later download from the same page is offered as an update of the one mod installed from it.
- **Updates.** Mods from GitHub with a release tag are checked against the repository's latest release: `rmm link updates`, `check_link_updates`, and the window's Check for updates (no Nexus sign-in needed for them). The new release's file is the only archive, the one with the same name, or the one whose name matches once version numbers are taken out; otherwise the user picks it. `rmm link update <id>`, `update_from_link` and the window's Update download it and update the mod in place, as one undo step. Hold pins the mod as for Nexus; Skip (`rmm link skip <id> <version>`) passes over that release.

## Import and lockfiles

**Import** brings in a setup from MO2 or Vortex, into the active profile as one undoable step (`import_mo2`, `import_vortex`; CLI `rmm import`; the profile menu in the window). The formats are written up in `docs/internals/mo2.md` and `docs/internals/vortex.md` (§9.4 in each).
- What comes over: mod folders (hard-linked when they share a volume, copied otherwise), names, Nexus ids, FOMOD choices, notes, mod order and enabled state, separators, plugin order and locks, MO2's row colours, and Vortex's mod rules.
- MO2: an instance folder (with `ModOrganizer.ini`) and one of its profiles (MO2's selected one unless named; the window asks when there are several), or all of them (`--all`, `all`, the window's "All profiles"), each into the rmm profile of its name, made when missing; the active profile stays the active one. A mod's `comments` and `notes` (MO2's notes editor writes HTML; rmm keeps the text) become its note, `color=` (a QColor in Qt's INI form) its row colour, and `ignoredVersion=` a skipped version, which update checks don't offer. Files MO2 hides (`.mohidden`, or in a folder so named) come over hidden (`.rmm-hidden/`, under their own names), as if hidden in rmm.
- MO2's profile options come too: with `LocalSettings` the profile's own INIs go into the rmm profile's (`profiles/<name>/ini/`) and its own INIs option is turned on; with `LocalSaves` the profile's saves are copied into `Saves/<profile>/` in My Games and its own saves option is turned on. Files already there stay.
- MO2's Executables become tools, leaving out the game, its launcher and script extender (Play starts them), Explore Virtual Folder, hidden ones, missing programs and programs already a tool. One rmm has a preset for (xEdit, QuickAutoClean, BodySlide, Pandora, PGPatcher, TexGen, DynDOLOD, xLODGen) gets the preset; others keep MO2's arguments and working folder. A program inside a mod runs from the deployed Data folder. A mod a program made (no archive, and named as that tool's output, or the mod MO2 has it write into: `[custom_overwrites]` in the profile's `settings.ini`) becomes the tool's output, so its next run replaces it in its place.
- Vortex: its live state (the `state.v2` LevelDB folder in `%APPDATA%\Vortex`, read from a copy; close Vortex first) or a full state backup (`temp/state_backups_full/*.json`). The staging folder and profile default to the ones Vortex last used.
- `find_import_sources` lists MO2 instances and Vortex state in their usual places.
- The dry run (the window's preview) says what it costs: the files, and the bytes copied rather than linked (another drive than the instance); MO2's hidden files and its Overwrite; mods already installed under an imported id, with both versions and file counts (`clashes`; the installed one stays); and the profile's mods the import doesn't name, which stay after it and win their conflicts (`after`).
- Mods go in under their own names. One already installed under that id is left as it is, so importing again only adds what is new.

**Lockfiles.** `export_lockfile` writes the active profile to `modlist.lock.toml`, so a setup can be checked or rebuilt on another machine. Each mod records its archive (name and sha256), its FOMOD choices, its Nexus ids and a fingerprint of its installed files; the mod order, enabled state, colours, plugin order and mod rules come along. `apply_lockfile` installs what is missing from archives found in the given download folders, lists what still has to be downloaded, and sets the order. Mods the user added that the lockfile doesn't list are kept, each after the mod it followed, so updating a curated list doesn't throw away personal additions.

A lockfile also records mod notes and `env`: the game exe's version, the script extender's runtime DLLs and the game versions Address Library has files for; applying one warns when the game or script extender differs, and fills in notes and Nexus ids an installed mod lacks. `export_lockfile{format}` writes `toml` (the default), `pack` (`modlist.pack.zip`: the lockfile and `mods/<id>/` for every mod no archive brings back: made by hand, from Overwrite or a folder, and a tool's output when it is plugins only, like an xEdit patch; other tool output is rebuilt by running the tool) or `markdown` (`modlist.md`, a readable list). `apply_lockfile` reads a pack too and installs its mods from it. `diff_lockfile{path, other}` (`rmm lock diff`) compares a lockfile with the profile now or another lockfile: versions, and mods and plugins added, removed, changed, turned on or off, and moved (those outside the longest run kept in order).

## LOOT

Sorting uses the `libloot` crate (0.29, pure Rust, GPL-3.0-or-later).

- **Masterlist.** The masterlist and prelude come from the `v0.29` branch of `loot/skyrimse` or `loot/fallout4`, and of `loot/prelude`. They are cached in the instance's `loot/` folder.
  - `sort_plugins` refreshes them when they are more than a day old. `update_masterlist` refreshes them on demand. Both download with `curl`.
  - If a download fails, the cached copy is used. With no masterlist at all, sorting falls back to plugin masters and record overlaps, with a warning.
- **Userlist.** `loot/userlist.yaml`, in LOOT's format, adds the user's own rules, so LOOT itself reads the same ones. `set_loot_rule` (CLI `rmm rule <plugin> --after X --group G`) replaces a plugin's load-after list and group, and an empty rule removes them; other user metadata for the plugin stays. Groups must exist in the masterlist. The userlist is not in the profile's undo history, so the call returns the previous rule. `loot_rules` lists the rules for the profile's plugins.
- **Groups.** `loot_groups` (`rmm group`, the window's **LOOT groups…** beside Sort with LOOT) lists the masterlist's groups with their descriptions, the groups each loads after (LOOT's and the user's apart), and the profile's plugins in each. `set_loot_group` (`rmm group <name> --after X`) adds load-after groups to a group, or makes a group of the user's own, which a plugin's rule can then use; `--remove` takes the user's version out. A change that would make a circle of groups is refused, naming the path that already goes the other way, and a group of the user's can't be removed while a rule or another group uses it. Like rules, groups are in the userlist and not in undo history.
- **What LOOT sees.** Sorting sees the profile, not only what is deployed.
  - The enabled mods, plus `overwrite/`, are passed to libloot as additional data paths, highest priority first. `file()` conditions and BSA/BA2 overlaps therefore follow the profile without a deploy.
  - Plugins are read from their mod folders.
  - libloot reads the profile's own plugins.txt, written to `loot/local/` before each use (`*` on the enabled ones), not the game's. So conditions on *active* plugins, the load order and Problems' LOOT messages follow the profile before a deploy. `undeployed` (how many plugins libloot saw on or off differently from the profile) stays as a check; the window's preview offers **Deploy, then sort again** if it isn't 0.
- **Result.**
  - A dry run returns the new order and the plugins that move: the fewest whose moving explains the new order (all but one longest run that keeps its order), so one plugin moved shows as one, not with every plugin that shifts along. Each comes with the plugin it then loads after, which the window's preview says in words ("SkyUI_SE.esp moves after …").
  - Otherwise the order is saved to the profile's plugin list, which is undoable, and reaches plugins.txt on the next deploy. Base-game masters always load first, so they are never added to the profile.
- **Why.** Each plugin that moves comes with LOOT's reason (`why`): the nearest plugin it passes that LOOT's rules put on its other side, then each rule on the way, in words ("Second.esp loads before First.esp: LOOT's masterlist says First.esp loads after it"). `rmm why <plugin>`, `explain_plugin_order` and the plugin panel's **Why here?** say where LOOT puts any plugin and the rules tying it to the nearest plugin before and after it; new plugins placed after an install (`place`) get the same.
  - The rules come from libloot's own log: while sorting it logs each rule it adds to its graph ("Adding Master edge from "A" to "B"."), and rmm reads those lines during the sort, one sort at a time. libloot has no other way to hand them out, so its version is pinned exactly (`=0.29.7`) and the LOOT flow test fails if the wording changes. libloot formats these lines whether anyone reads them or not, so reading them costs only the parsing.
  - Explanations use real rules only (masters, masterlist and user rules, groups, record and asset overlaps), never tie-breaks, which only keep the existing order. Two plugins that change the same records: the one that changes more records overall loads first, so the more specific one wins. When no rule moves a plugin by itself, the reason says the plugins around it moved. Master-flagged plugins sort apart from the others, so "it's a master file" stands in where no rule links the two.
- **Circles of rules.** When LOOT's rules contradict each other, nothing is sorted and the error (a `Cycle`) names each rule in the circle in words and the plugins in it that have rules of the user's. Nothing is set aside on its own: `sort_without` (`rmm sort --without <plugin>`, `sort_plugins{without}`) leaves the user's rules for those plugins out of that one sort, and the userlist keeps them. The window's preview shows the circle with **Sort without it** and **Remove your rule** for each of the user's rules in it. A circle among groups, or one with no rule of the user's, is only explained.
- **Health check.** It reports LOOT's warning and error messages, both general and per enabled plugin. It also reports dirty-plugin data, pointing to the `xedit-qac` tool. It uses only the cached masterlist and never downloads.
- **Batch cleaning.** `clean_dirty_plugins` (`rmm clean-plugins --apply`, Problems' **Clean dirty plugins…**, shown while LOOT reports a dirty plugin) runs the QuickAutoClean tool (the one whose arguments have `-qac`, from the `xedit-qac` preset) on every enabled plugin the cached masterlist knows as dirty by its CRC, one run after another, as MO2's Batch Plugin Cleaner does. Each run is its own undo step and puts the clean copy in its own "Cleaned <plugin>" mod, the original staying in its mod. With `one_mod` (`--one-mod`, the window's "All in one mod", ticked by default there), every clean copy goes into one "Cleaned plugins" mod at the end of the list: each run keeps the files the earlier runs put there, except the old copy of the plugin it cleans. Plugins whose only fault is deleted navmeshes, which QuickAutoClean can't fix, are listed for xEdit by hand. The report says which plugins LOOT still finds dirty after. Checked with SSEEdit 4.1.5f on a copy of the real Skyrim setup: ELFX lost its 2 ITMs and LOOT stopped flagging it; Reverb and Ambiance Overhaul, which the masterlist gives 1 ITM, xEdit found clean, and the report says LOOT still lists it.

## Archives, light plugins and game settings

- **Packing** (`pack_mod`, `rmm pack <mod> [--plugin P] [--apply]`, the mod panel's and plugin panel's **Pack into archives…**) puts a mod's loose files into archives named after one of its plugins, as MO2's packer does: Skyrim SE `<plugin>.bsa` and `<plugin> - Textures.bsa` (version 105, uncompressed, 2 GB each at most), Fallout 4 `<plugin> - Main.ba2` (GNRL, zlib except sound) and `<plugin> - Textures.ba2` (DX10). The writers are rmm's own; their name hashes match Bethesda's on real archives (an ignored test reads them, `RMM_REAL_BSA`, `RMM_REAL_BA2`). Script extender plugins, other files the game only reads loose, non-ASCII paths and Fallout 4 textures that aren't DDS stay loose. The plugin defaults to the mod's masters first, then the shortest name. Packed files lose to every loose file, so the report lists `loses`: files another mod has that this one wins now. Applying is one undo step (the loose files are kept in trash) and takes effect at the next deploy. An archive name already in the mod is refused.
- **Light plugins.** `light_candidates` (`rmm light`) lists the plugins that could be flagged light: their new records fit a light plugin's form ids and they add no cells or worldspaces (which break when light on Skyrim SE). `set_light_flag` (`rmm light <plugin> [--off]`, the plugin panel, Problems' **Flag them light…**) sets or clears the TES4 header's light flag in the mod's file, as one undo step. Only candidates can be flagged, and an `.esl` keeps its flag. It is for a new game: a save that uses the plugin loses what it added.
- **Form 43.** On Skyrim SE, Problems warns about enabled plugins saved by Skyrim LE (form version 43, below 44), which can crash or lose data until resaved in the Creation Kit.
- **Game settings** (`game_settings`, `set_game_setting`, `rmm game-settings [section key value]`, Settings' **Game settings…**) shows common INI settings as a form: display, interface, controls, saves, mod-related ones (archive invalidation and file selection on Fallout 4, the grass cache on Skyrim SE) and Papyrus logging, each with its kind, range and default. Values are read as the game does (Custom over Prefs over the main INI). A change is checked against the range and written to the file that holds the key, else Prefs, through the workspace's writes, so each is in Edits; the window's toast puts a save back.

## In-game test harness

`harness/skse` (CommonLibSSE-NG) and `harness/f4se` (CommonLibF4) are two small C++ plugins, `rmm_harness.dll`, with their shared part in `harness/common`. `harness/README.md` says how to build them. The user installs the DLL as a mod (`SKSE/Plugins` or `F4SE/Plugins`). `test_run` sets `RMM_HARNESS_PORT` and `RMM_HARNESS_TOKEN` for the game, which the loader passes on. The plugin then connects back over **TCP 127.0.0.1**, which works through Proton, unlike named pipes. Without those variables it does nothing. The protocol is JSON lines:

- **Plugin → manager:**
  - `{"ev":"hello","token":"…","runtime":"1.6.1170","console_output":true}` (a wrong token is turned away; `console_output` says results of console lines carry what they printed)
  - `{"ev":"data_loaded"}`
  - `{"ev":"main_menu"}`
  - `{"ev":"game_loaded","save":"…"}`: a loading screen closed with the player in the world, after a save or a `coc`
  - `{"ev":"heartbeat","fps":58.2,"cell":"…"}`, every second
  - `{"ev":"note","what":"MainMenu opened"}`: a step on the way (a menu opening or closing, data starting to load). rmm keeps the last 12 and names them when a wait gives up, so a timeout says where the game stopped
  - `{"ev":"result","id":N,"ok":true,"out":"…","data":{…}}`: `out` is why it failed, or what a console line printed; `data` is what a playing command answers
  - `{"ev":"game","what":"death","actor":{…},"killer":{…}}`: the game's events as they happen: `death`, `activate` (the player's only), `combat` and `stage` (Skyrim), `hit` (on or by the player; Fallout 4). rmm keeps the last 200 and hands them to the step they happened during
- **Manager → plugin**, run on the game's main thread:
  - `{"id":N,"cmd":"load_save","name":"…"}`
  - `{"id":N,"cmd":"console","line":"coc Riverwood"}`
  - `{"id":N,"cmd":"screenshot","path":"…png"}`: a PNG of the game's window, read with `PrintWindow`, so it works while other windows cover the game
  - `{"id":N,"cmd":"quit"}`
  - the playing commands, which answer with `data`: `state`, `papyrus`, `walk`, `activate`, `face`, and in Skyrim `dialogue`, `choose`, `menu_call`, `menu_get`, `act`, `press` (see the steps below). A plugin without one answers that it doesn't have it

**Console output.** A console line's result carries the text it printed, and the step's result has it as `output` (`""` when nothing was printed; missing with a plugin that predates this). The line runs in console mode, as if typed, since some commands print only then.
- Skyrim: every printed line goes through `ConsoleLog::VPrint` (Address Library 50180 / 51110). In a game rmm started, the plugin puts a detour on it: a 5-byte jump to its own function, which copies the lines printed on the main thread while rmm's line runs, then calls the original through a stub holding the moved first instruction. It does this only when the function starts with the 16 bytes it has on 1.6.1170 (the ones Console Link checks for), so another runtime or another plugin's hook there is left alone. Then it falls back to the text the console log's buffer gained during the line. Which one is in use is a note at the start (`console output: hooked`).
- Fallout 4: the game prints a command's result some frames after `Console::ExecuteCommand` returns, so the plugin answers 150 ms later with the text `ConsoleLog::buffer` gained, less the game's echo of the line (`<line>` and `Command: <line>`). The shared harness takes this through `Game::console_later`.
- Lines other plugins print while rmm's line runs come along too (some mods log condition checks to the console on every cell load).
- Checked in Skyrim AE 1.6.1170 (SKSE 2.2.6) on the 50-mod test setup: in Riverwood, `player.getav health`, `getstage MQ101`, `player.getpos x`, `getglobalvalue gamehour`, `player.getitemcount f`, a 150-line `help riverwood 4` and an unknown command ("Script command … not found.") each came back with exactly their own lines. In Fallout 4 1.10.163 (F4SE 0.6.23) in QASmoke: `player.getav health` ("GetActorValue: Health >> 85.00"), `getgs fJumpHeightMin` and `tgm`. Not checked yet: the Skyrim fallback (the buffer, while the console is closed), and whether Fallout 4's buffer is capped (a capped buffer that drops its oldest text would lose output).

`test_run` (CLI `rmm test-run`) goes through these steps:
1. Deploy.
2. Launch through the script extender.
3. Wait for `main_menu`, with a timeout. Fallout 4 can open its main menu before its data has loaded, so its plugin reports `main_menu` once both are done; it watches menus from `kInputLoaded` and also counts a main menu that opened before that.
4. Optionally load a save, then `coc` through a list of cells, waiting for each to load and sampling FPS. Without a save, the first `coc` starts the game from the main menu. A cell that never loads is reported against it.
5. Quit, unless asked to leave the game open.
6. Parse the crash logs, the Papyrus log, and the script extender's log for plugins that didn't load (`plugins_not_loaded`, each with why and its mod).

Every wait (for the harness to connect, for an event, for a command's answer) also checks a few times a second for a Windows message box open in a program from the game's folder: the game, or the script extender's loader, as when a plugin's DLL is missing a dependency. rmm reads its title, text and buttons from the window (`EnumWindows`, then the dialog's `Static` and `Button` children), so the game can stay behind other windows, and ends the wait at once with "the game stopped on a message box: Plugin error: … [Yes / No]" instead of running out its timeout. Nothing is clicked; the game is then closed as at the end of any run. A live session ends the same way, with the box's text as `ended`.

The game runs in a small window behind the others, so a run doesn't take over the screen. `window` is `"WxH"` (default `960x540`, the smallest size whose screenshots still show the HUD and the scene clearly) or `"fullscreen"` for the game's own settings. For the run rmm sets `[Display]` in `<game>Prefs.ini` to a bordered window of that size, and `bAlwaysActive=1` under `[General]` in `<game>.ini`, and writes both files back byte for byte once the game has exited, along with `<game>Custom.ini`, which a windowed Fallout 4 writes its window position into (the game saves its prefs on exit, so `keep_open` keeps the game's own settings). The game reads `bAlwaysActive` only from the main INI and only at start; without it an unfocused game stops its clock and draws black frames. `RMM_HARNESS_BEHIND` tells the plugin to send the window to the back without focusing it, with `SWP_ASYNCWINDOWPOS`: it does so from the UI thread as the main menu opens, and a `SetWindowPos` that waits for the main thread (which owns the window) while the main thread waits on the UI thread froze about one start in three, right after data loaded. The plugin also sets `bAlwaysActive` in memory, so its commands keep running in a fullscreen game that loses focus. With `screenshots`, rmm saves a PNG after loading the save and in each cell, into `test-runs/<time>/`.

A scenario can also carry `steps`, a test plan run after the save and the cells. Each step is one of:

- `{"cell": id}`: `coc`, then wait for the load.
- `{"console": line}`: any console command. What it prints is the step's `output`, so queries such as `getstage`, `player.getav`, `player.getpos` and `sqv` answer.
- `{"wait": seconds}`: let the game run, sampling FPS.
- `{"screenshot": name}`: a PNG of the window.
- `{"load": save}`: load a save and wait for it.
- `{"state": {"quests": [], "items": [], "refs": [], "radius": 3000}}`: the game's state as data. The player (cell, position, heading, level, combat, weapon drawn, health and magicka/stamina or action points as [now, max]), open menus, the nearest 20 actors from the high process list (ref, name, base, distance, dead, hostile, health) and 25 objects (doors, containers, furniture, flora, items, terminals; Skyrim by range, Fallout 4 from the player's cell), then the quests (stage, running, completed), items (counts; Skyrim) and refs asked for. Refs are form ids in hex, editor ids or `player`.
- `{"wait_for": {"dead", "stage": {"quest", "at_least"}, "menu", "menu_closed", "in_combat", "near": {"ref", "within"}, "cell", "timeout"}}`: polls the state every 500 ms until every condition given holds, or fails after `timeout` seconds (default 60) naming what didn't.
- `{"call": {"class", "fn", "self", "args"}}`: calls a Papyrus function through the game's VM. The plugin finds it in the class (and its parents, for methods), converts `args` by the parameter types (forms by id or editor id, packed as script objects of their own type), dispatches it, and answers when it returns, with its value (forms as `{form, name}`). A wrong count or type answers with the signature. Fallout 4 1.10.163's VM takes its own function object for the arguments, which the plugin has the game make (`Papyrus::detail::CreateThreadScrapFunction`); next-gen takes a `std::function`.
- `{"move_to": ref}`: walks the player straight at the ref with the game's auto-move (`PlayerControls::data.autoMove`), turning toward it when off by more than 10 degrees, until 100 units away. When the player gets no closer for 3 seconds, the player is moved there (`MoveTo`; `player.moveto` in Fallout 4) and the data says `moved_from` and why. Held keys sent from outside the input loop reach the game on some frames only, and `Actor.PathToReference` doesn't move the player even AI-driven, so neither is used.
- `{"activate": ref}`: `TESObjectREFR::ActivateRef` with the player: doors, containers, items, and NPCs, whose conversation opens.
- `{"face": ref}`: turns the player toward it (`SetHeading`, so the camera turns too).
- Skyrim only, each answering in Fallout 4 with the list of what it has:
  - `{"dialogue": {}}`: the Dialogue Menu's topics from `MenuTopicManager` ({index, text, new}) and the speaker.
  - `{"choose": index or words}`: selects the topic in the menu's own list and calls its click handler (`_root.DialogueMenu_mc.onSelectionClick`), then waits until the menu is back to its topics or closed (up to 60 s) and answers with what was said (the menu's subtitle text, when the game shows dialogue subtitles) and the topics after. Calling the game's `TopicClicked` callback directly leaves the menu waiting for a click it never saw.
  - `{"button": n}`: a message box's button (`buttonPress`).
  - `{"menu_call": {"menu", "callback", "args"}}`: `gfx.io.GameDelegate.call(callback, args)` on the menu's movie, as its buttons do; a callback starting with `_root` is invoked as an ActionScript function instead (`_root.DialogueMenu_mc.onCancelPress` leaves a conversation).
  - `{"menu_get": {"menu", "path"}}`: an ActionScript variable; an object lists its members, so a menu can be explored.
  - `{"attack": {"target", "kind"}}`: faces the target, draws the weapon, and performs the action (`TESActionData` with the BGSAction form: attack, power_attack, left_attack, dual_attack, release...), as the controls would.
  - `{"press": {"control", "ms"}}`: `ButtonEvent`s for a control by its Controls-menu name through `BSInputDeviceManager`, for `ms`. In the world the key goes into the input the game hands `PlayerControls` and `MenuControls` each frame (a vtable hook on each, installed at the first held key and only after the vtable's RTTI name checks out): a key sent on its own from a task lands elsewhere in the frame, and the player, whose movement is rebuilt from each frame's input, then walks only on the odd frame. In a menu the events still go out from a task, which menus take. The result (and `key`'s) says how the player moved meanwhile, to tell where walking stops: `moved` (units), `input` (the largest `PlayerControls` move input, 0 to 1: 0 means the key never reached the movement handler), `anim_speed` (the largest `Speed` the animation graph asked for: 0 with input means the behaviour didn't start walking), `controller_speed` and `controller` (the character controller's speed in units a second and its states: a speed with nothing `moved` means something holds the body). `move_to` adds the same as `motion` when it gives up walking and moves the player.
  - `{"click": {"x", "y", "button", "double", "wheel"}}`: a `GFxMouseEvent` move, then down and up (or a wheel turn), sent to the movie of the topmost open menu that uses a cursor, at window pixels. Over MCP, x and y are in the last screenshot the AI got and are scaled back by the factor that screenshot was shrunk by. Nothing goes through Windows' input, so the game can stay behind other windows. The result names the menu.
  - `{"key": {"key", "ms"}}`: a key by name, sent as a keyboard `ButtonEvent` with its DirectInput scan code and the user event the `ControlMap` binds to it in the current input context (then menu mode, then gameplay), so Escape is Cancel in a menu and E is Activate in the world. The result names the event.
  - An in-game message box (a mod's tutorial, a "requires" warning) pauses the game; when one opens, the step's `events` get `{"what": "message_box", "text", "buttons"}`, and `{"button": n}` answers it. `activate` on something that opens a menu (a book, a container) succeeds with the menu's name as `menu`.
  - `{"type": "text"}`: a `GFxCharEvent` per character to the topmost cursor menu's movie (search boxes, names). The text goes to the field with focus, so a search box is clicked first (tested in SkyUI's inventory).

Each step's result has ok or its error, FPS, the player's cell from the last heartbeat, the screenshot's path, `data` from a playing step, and the game's `events` during it (`rmm test-run --steps <json or @file>`).

Checked in Skyrim AE 1.6.1170 on the 50-mod setup, in Riverwood, the Bannered Mare and QASmoke: the state found Faendal, Gerdur and nearby objects; Papyrus calls returned the player, Health 100 and the game time; a Survival Mode message box was answered with `button`; `move_to` walked to Faendal and to a wolf indoors and moved the player past a rock; activating Faendal opened the conversation, `choose` by words and by index went through two answers and `onCancelPress` left; with a sword, `attack` and `power_attack` took a wolf from 400 health to 375; `press` moved the player and jumped; deaths, combat, the player's activations and quest stages came as events. In Fallout 4 1.10.163 in QASmoke: state, Papyrus calls (`GetPlayer`, `GetLevel`, `GetValue` with the Health actor value, game time), `move_to` a container 780 units away (walked, 94 away), `activate` opened its ContainerMenu, `face`. Not checked in Fallout 4: events from deaths and hits.

**Live test sessions** (`test_session_start`, `test_session_step`, `test_session_stop`; MCP only) keep the game open between batches of steps, so an AI can look at each screenshot and decide what to do next. Start launches and connects like `test_run`, waits for the main menu, then plays the save, cells and steps it was given. Screenshots are always on. Each step call returns its results, then each screenshot as an image (MCP image content, in step order), so an AI sees the game without opening files; one wider than 1280 pixels is scaled down by a whole factor (averaging each block), which keeps an image near 1,200 tokens. The chat log keeps only the text. If the game has closed, the call ends the session itself and returns the whole run with the crash log read back to mods. Stop quits the game, reads the logs and puts the INIs back. One session runs at a time. If the client disconnects without stopping, dropping the session closes the game and puts the INIs back.

**The tester on Haiku** (`rmm tester-agent`; `--apply` writes it): a Claude Code helper agent, `rmm-tester.md` in `~/.claude/agents/` (or `--dir`), with `model: haiku` and only the live test's tools (`mcp__<server>__test_session_*`, `plugin_records`, `mod_reviews`, `nexus_mod_info`, `read_crash_log`, `read_papyrus_log`, and Read). Its instructions are the tester prompt. Haiku is the cheapest Claude model, and every Claude model reads images, so it sees the screenshots. The `test_mods` prompt and the lead hand it the live test when the client has it: the lead plans and reads its report. rmm doesn't pick the model through MCP sampling, which few clients support; the agent file pins it. The MCP tab shows the command.

It returns pass or fail, the timings of each milestone, FPS (average and minimum) and the suspect mods. Without the harness it falls back to launching the game and checking the process and the logs. `read_crash_log` reads Crash Logger SSE, Buffout 4, Trainwreck (`crash-<time>.log`) and NetScriptFramework (`Crash_<time>.txt`) logs, not plugins' own logs such as `CrashLogger.log` or `CrashFixCompendium.log`, and ranks the mods that provide the plugins, files and DLLs they name. Its `next_steps` say what to try in plain words: for the top suspect from a mod, by kind (a script extender DLL built for another game version, a plugin's masters or place, a broken mesh or texture), that a suspect's mod is disabled now, a game version that differs from the log's, and with several suspect mods, turning half of them off at a time. For a DLL no mod provides that sits in `Data/SKSE/Plugins` (or `F4SE`) or the game folder, they say where, and that something outside rmm put it there; only when the log names nothing at all do they suggest the save. `not_yours` gives the reasons a log may not come from this setup: rmm hasn't started the game here yet (no `game-version.txt`), the log is older than rmm's first Play (that file's creation time), its PLUGINS section lists a number of plugins more than 2 away from the profile's (`plugin_count`), or the crash logger that wrote it (its version on the logger line) differs from the installed DLL's file version. With any of these, the first step says the log may not apply and to read the next one; the window's crash log dialog shows the reasons above the suspects. `rmm crash-log --text` prints the report to paste into a post. `support_bundle` (CLI `rmm support-bundle [--dir] [--crash]`) saves `rmm-support-<time>.zip`: `summary.md` (the setup, the crash report, the problems, script extender plugins that didn't load, parts left out), the crash log, `health.json`, the script extender and Papyrus logs (the last 1 MB of each), `modlist.lock.toml`, `deploy-plan.json` (the first 200 of each file list, with counts) and `settings.json` without the AI role notes. Both take the Windows user name out of `\Users\<name>\` and `/home/<name>/` paths. `read_papyrus_log` groups the Papyrus log's errors by message and by script.

The Rust side is tested against a stand-in plugin. The Fallout 4 plugin has run in Fallout 4 1.10.163 with F4SE 0.6.23 on Windows: main menu after about 13 s, `coc` into RedRocketExt and Vault111Ext at 40 to 46 FPS on average in a 960x540 window behind the others, screenshots, quit, and all three INIs put back. Its first run found three bugs, all fixed: the plugin only watched menus from the first `kGameDataReady`, which comes as loading starts and after the main menu has opened; `close` compared the exe path as text, so an instance whose game path uses forward slashes left the game running after a failed run; and screenshot paths were relative to the instance, which the game resolves against its own folder. The Skyrim plugin has run in Skyrim AE 1.6.1170 with SKSE 2.2.6 on Windows: main menu after about 22 s, `coc` from the main menu into Riverwood and Breezehome at 53 to 58 FPS in a 960x540 window behind the others, screenshots, a cell that doesn't exist reported against it, quit, and both INIs put back. Under Proton (Steam's Proton Experimental 11 in WSL Ubuntu 26.04) the Skyrim plugin loads through SKSE and connects back to rmm over TCP from inside Wine, which is what the design rests on; the game couldn't draw there (see M6), so the rest of the run is untested under Proton. The Fallout 4 plugin builds but hasn't run in the game yet.

**Finding the culprit** (`bisect`; CLI `rmm bisect start|crashed|ok|run|status|stop`; the crash log dialog's **Find the culprit…** and a bar under the tabs) halves the suspects until one is left. Start takes the mods the newest crash log names, the mods given, or all enabled mods; from the first and last, never the mods with the script extender, Address Library, a crash logger (`launch::essential_mods`) or the harness, without which nothing else loads or no crash log is written. Each step turns off half of the mods still suspected, together with the enabled mods that need them (their plugins use the step's plugins as masters, or their rules require them), as one undoable change labelled `bisect step <n>: …`; from the end of the list, since later mods are the ones that need earlier ones. After the game is played to where it crashed, `crashed` or `ok` undoes the step and keeps the half that still holds the culprit. `run` plays every step with `test_run` instead (a failed run counts as a crash). When one mod is left and a step with it off didn't crash, that's the culprit; until some step passes, the last mod left gets a step of its own, so a crash none of the suspects causes ends in "not found". A change made during a step (other than undoing it) stops the next mark: rmm won't undo over it. `stop` turns the step's mods back on and ends it. The state is `profiles/<name>/bisect.json`.

## Add-ons

Add-ons are **Extism (WASM)** plugins: sandboxed, cross-platform, and writable in Rust, JS, Python, Go and other languages. Each add-on is a folder in `<instance>/addons/` with `addon.toml` and `addon.wasm`. It has no files, processes or network of its own (no WASI). It reaches rmm through one host function, `rmm`, in Extism's user namespace: JSON in (`{"op": …}` plus arguments), `{"ok": …}` or `{"error": …}` out.

```toml
name = "my-addon"
version = "0.1.0"
description = "What it does"
capabilities = ["read_instance", "modify_profile"]   # also mod_files, run_tools, network
hosts = ["*.nexusmods.com"]                          # what network may reach
hooks = ["after_install", "health_check"]
timeout = 60                                         # seconds per call (default 60)

[[tools]]
name = "list_big_mods"
description = "Mods with more than N files"
input = { type = "object", properties = { min = { type = "integer" } } }

[[panels]]
title = "Big mods"
function = "big_mods_panel"
```

- **Capabilities** decide which operations the host function allows:
  - `read_instance`: `info`, `list_mods`, `list_plugins`, `list_conflicts`, `mod_files {id}`
  - `modify_profile`: `set_mods_enabled {ids, enabled}`, `move_mods {ids, priority}`, `set_plugin_enabled {name, enabled}` (undoable like any change)
  - `mod_files`: `read_file {id, path}` (base64), `write_overwrite {path, base64 | text}`
  - `run_tools`: `run_tool {id, dry_run}` (a dry run unless `dry_run` is false)
  - `network`: Extism's `http_request`, only to the hosts listed
- **Hooks** are exported functions named after the moment they run, given JSON: `after_install {id, name}`, `before_deploy {}` (return `{"abort": "why"}` to stop it), `after_deploy {linked, removed}`, `after_tool_run {tool, mod}`, `health_check {}` (return `[{"severity", "subject", "message"}]`). A hook's error becomes a warning on the operation. Hooks run outside the instance lock, and not while an add-on is running, so an add-on's own changes can't loop.
- **Contributions:** `tools` (functions that AI clients call through `call_addon` and the window lists, each with an input schema) and `panels` (a function whose `{"text"}` or `{"columns", "rows"}` result the window shows).
- **Install** (`rmm addon install <dir>`, the window's Add-ons dialog) validates `addon.toml`, loads the module once, and shows the capabilities it asks for before copying it in. Memory is capped at 256 MiB.

A Rust add-on with `extism-pdk` looks like this (a sketch, not compiled here):

```rust
use extism_pdk::*;

#[host_fn]
extern "ExtismHost" { fn rmm(input: String) -> String; }

#[plugin_fn]
pub fn list_big_mods(input: String) -> FnResult<String> {
    let mods = unsafe { rmm(r#"{"op":"list_mods"}"#.into())? };
    Ok(mods) // filter by the input's `min` here
}
```

**Games from add-ons.** An add-on can add games with `[[games]]` in addon.toml; an add-on that only does that needs no wasm. A game added this way is a relative of a built-in one (Skyrim VR, Fallout 4 VR, Enderal SE): it follows its `base` game's rules for archives, plugins, the script extender's folders, health checks and tool presets, and has its own executable, loader, Steam id and folders, INI and Nexus domain. `loadorder` picks libloadorder's game where the relative has its own (`SkyrimVR` or `Fallout4VR`), which also picks LOOT's game and masterlist and xEdit's mode.

```toml
[[games]]
id = "skyrimvr"                 # Vortex's id where it has one
name = "Skyrim VR"
base = "skyrim-se"              # or fallout4
loadorder = "SkyrimVR"          # optional: the base's by default
exe = "SkyrimVR.exe"
loader = "sksevr_loader.exe"
steam_app_id = 611670
steam_dir = "SkyrimVR"          # under steamapps/common
local_dir = "Skyrim VR"         # %LOCALAPPDATA% and My Games folder
ini = "SkyrimVR.ini"
nexus_domain = "skyrimspecialedition"
```

`rmm init --game skyrimvr --addon <folder>` creates an instance for it and installs the add-on there; opening the instance later reads its add-ons' games before `instance.toml`. Games other than relatives of the two built-in ones need code: rmm's archive, plugin and launch rules are written for those two.

## Saves and edits

- **Deleting saves.** **Delete…** on the Saves tab (or a save's right-click menu), `delete_saves`, or `rmm saves --delete <files>` moves each save with its co-save to `trash/saves/<profile>/`, a number added to a name already there. Emptying the trash deletes them.
- **Orphaned co-saves.** `rmm saves` lists the script extender co-saves whose save is gone (`orphans`). `rmm saves --clean-cosaves --apply`, or Clean co-saves on the Saves tab, moves them to `trash/co-saves/<profile>/`. Emptying the trash deletes them.
- **Edited mod files.** Each edit made through rmm records a SHA-256 of what it saved. `workspace::live_edits` finds a mod's files that still hold one of its edits; reverts don't count. The window asks before updating or reinstalling such a mod, and the install report names those files afterwards.

## Installer and updates

`crates/rmm-app/tauri.release.conf.json` turns on the bundler:
- A per-user NSIS installer, with `rmm.exe` as a sidecar beside `rmm-app.exe`.
- `installer-hooks.nsh` puts the folder on the user's PATH.
- Updater artifacts are signed with the key in `TAURI_SIGNING_PRIVATE_KEY`.

The base config holds the updater's endpoint (`latest.json` of the newest GitHub release) with an empty public key. A hand-built rmm therefore says it can't update itself.

`.github/workflows/release.yml` builds a draft release for each `v*` tag. It signs the installer with a code-signing certificate when the secrets are set.

## Desktop app

`crates/rmm-app` is a Tauri 2 shell. The window is plain HTML, CSS and JavaScript in `ui/`, with no bundler. Every action is one `call(name, args)` into rmm-core, so the window, the CLI and the MCP server share one code path and one undo history. Calls run off the UI thread.

- **Mods:** the priority list with drag and drop (pointer events, since the window keeps the operating system's file drop for installs), enable checkboxes, and conflict markers. Selecting a mod marks the mods it wins against and the ones that win against it (MO2's highlight), and opens a panel with its categories, conflicts, rule, files and where it was installed from. The Content column (on by default) shows icons for what a mod holds (plugins, script extender DLLs, scripts, meshes, textures, animations, interface, sound, archives and more); clicking one filters to that tag. The Category column (on by default) shows each mod's labels; clicking one filters the list to it (`#armour` in the filter does the same), and the panel adds and removes them, for several selected mods at once too. Broken mod rules show a warning and a "Sort by rules" preview.
- **Long lists** (the P0 items in `reports/MO2 and Vortex UI at scale.md`):
  - Both lists draw only the rows on screen (fixed-height rows, fixed column widths), so 3,000 mods paint in a few milliseconds.
  - Separators collapse (remembered per instance in the window's storage) and take a colour. A closed group shows how many of its mods lose conflicts, are overridden, or break a rule or miss masters.
  - Selection: click, Shift and Ctrl, the arrow keys, Ctrl+A. Space enables or disables, Delete uninstalls (when the newest save was made with the mods' plugins, it says so and offers Disable instead), Ctrl+Up/Down moves (a group hops whole groups so none is split), F2 renames a mod or separator. Keyboard moves show at once and are sent once the keys stop (350 ms), as one step, so holding Ctrl+Down keeps up. Dragging several rows keeps their order; dragging a separator takes its group.
  - "Move to": top, bottom, the end of a group, after a named mod, before its first conflict or after its last.
  - The plugin list takes the same keys: Shift and Ctrl selection, the arrow keys, Ctrl+A, Space, Ctrl+Up/Down (the selection moves together), dragging several, and "Move to" (after a named plugin, the top or the bottom); several plugins change as one undo step (`set_plugin_enabled` takes `names`, `rmm plugins --enable a --enable b`). An Index column gives each plugin's load-order index as xEdit shows it (`1A`, `FE 003` for light plugins). The plugin panel's **Record conflicts** (`record_conflicts`) lists the plugins that change its records, the last to load (the winner) first, with how many records each shares, how many are identical copies, and whether it's a patch.
  - **File conflicts** (a row's menu) starts in plain words: the mod lower in the list wins, a loose file beats an archive. Then a line per mod it shares files with gives the kinds of file (scripts, meshes, plugins…), who wins, and **Expected** (a patch that wins over what it patches, going by its name; or two mods that only change looks and sounds) or **Worth a look** (a patch that loses, or scripts, plugins, menus, animations or settings where only the winner's are used).
  - Row colours show as a solid stripe at the row's left edge over a stronger tint, separators' too.
  - Right-click menus on mod and plugin rows: enable, disable, move, rename, reinstall, update from Nexus, update from a file, file conflicts, hide files, notes, open folder (`open_mod_folder`), colour and categories (for several rows too; several rows' colours are one undo step, `set_color{ids}`), uninstall; lock and the plugin's mod; collapse or expand every group (also Ctrl+Left/Right). A file-conflict row has **Hide** for the mod's own loose copy.
  - Windows inside the window: dragging a tab off the tab bar (a frame shows where it lands), or its right-click menu's **Open in a window**, pulls it out into a window over the main view. Its title bar moves it, its edges and corners resize it, and a click on it or its tab brings it to the front; **Tab** (or the tab's menu) puts it back as a tab. Dropping a tab or a window on the main view's left or right edge, or its bottom, docks it there (a highlight shows the area first), as do the tab menu's **Dock on the left / right / at the bottom**: docked panes share their edge's area, whose inner edge drags to resize it, and **Window** or dragging a docked pane's title bar makes it a window again. The tab bar marks pulled-out tabs (⧉), and one tab always stays in the main window; Mods, with the plugins beside it, never leaves it. A pulled-out pane stays live: reloads redraw it, selecting a plugin or mod in one shows its details in the side panel, and the keys go to the list clicked last. The windows' places, sizes and docks are kept with the window's other preferences and come back with it, apart from tabs the Simple view hides.
  - Rows are compact by default (Settings, Rows: Comfortable makes them taller).
  - Shortcuts: Ctrl+1 to 9 for the tabs shown (their tooltips say which), Ctrl+, Settings, Ctrl+D Deploy, Ctrl+P Play, F5 reads the instance again (as MO2's F5 refreshes), Ctrl+Z and Ctrl+Y.
  - Filters: text (debounced; words must all match, `-word` leaves out, `a | b` takes either) plus enabled, disabled, conflicted, overridden, broken rule, missing masters, has plugins, and installed in the last 7 days; the chips' link button switches between All (every chip must match) and Any. The bar shows "x of y mods" with Clear and enable or disable all matching; Ctrl+F and Esc. Rows a filter or a closed group hides leave the selection, so bulk actions never reach them.
  - The mod rule picker is a type-ahead over mod names instead of a list of every mod.
  - Enable and move show their result at once and the reload follows. On the 3,000-mod fixture (release build, warm) `state` takes about 550 ms: its three slow parts run side by side, and conflict lists cross the bridge as priorities instead of ids (3.0 MB down to 0.8 MB). The deploy preview (about 0.9 s) and the health check (about 1.5 s) run after the list is drawn.
- **The mod panel** also renames the mod, keeps its notes, sets its row colour, and reinstalls it (through the FOMOD wizard, starting from the stored choices). `overwrite/` has its own row: list its files, make a mod from them, or clear it.
- **Plugins:** beside the mods on the Mods tab (they have no tab of their own; the edge between the two lists drags to share the width, and a double-click puts it back; a narrow list leaves out its From column): load order with drag and drop, base-game plugins locked at the top, missing masters, plugin locks, LOOT user rules, and a LOOT sort shown as a preview first.
- **Problems** (the health check, re-run after changes settle, plus the crash log and Papyrus log readers, and **Support bundle…**; the crash log dialog lists what to try under the suspects, with **Copy report**, **Save support bundle…** and **Find the culprit…**, whose steps show in a bar under the tabs with It still crashed, It didn’t crash, Test each step for me… and Stop; and **Test run…**: a save or cells to visit, seconds in each, the window size and screenshots; the result shows pass or fail, timings, FPS per cell, crash suspects linked to their mods, Papyrus errors and the screenshots) Failed installs, Plays and Nexus downloads are listed there too until dismissed. **History** (the profile's changes with their times, "Restore to before…" on each, Deployed and Played markers where they happened, the undone steps Redo brings back above them, and a note once the step limit drops old ones; Restore's preview lists the mods it puts in the trash). The Undo and Redo buttons' tooltips name the step they undo or redo. Problems says LOOT's messages show once its masterlist is downloaded only while it isn't (`instance_info`'s `masterlist`). Undo and Redo also work with Ctrl+Z and Ctrl+Y.
- **Data** (MO2's Data tab): one folder of Data at a time, as the game sees it after a deploy, with a breadcrumb path. Folders show how many files they hold. Each file shows the mod that wins it, any archive it comes from, and the mods it beats; files no mod provides are the game's own or were put there by hand. "Conflicts only" keeps files more than one mod provides, "Archives" adds the files inside the BSA/BA2 archives the game loads, and the search box finds paths in every folder (the first 1,000), opening a file's folder on click.
- **Saves:** the profile's save folder (its own with "own saves", otherwise the INI's `sLocalSavePath`) with character, level, location and time. Only each save's header and the start of its body are read: Skyrim SE's is LZ4-compressed, and saves run to 100 MB. A save made with plugins the profile doesn't load says how many; the list names them with the installed mod that has each, and one button enables those (one undo step).
- **Downloads:** the instance's `downloads/` folder, where Nexus downloads go, with each file's mod on Nexus (when rmm downloaded or identified it, otherwise the mod and version its Nexus file name carries: the site's names now, older `<name>-<id>-<version>-<time>` ones, and ones without the time and with any version, such as `RDO Final-1187-Final`, where the id is the first number of 3 digits or more) and the mods installed from it (matched by file name). Install, reinstall the mod made from it, or delete the file; tick several (or all) to install or delete them together, or to identify them on Nexus. The download queue and failed downloads, with Retry, show above the list.
- **Tools:** add a tool from a preset, run it with a preview first, remove it.
- **Profiles** from a menu: switch, copy, new empty, rename, delete, own INI files and own saves, import from MO2 or Vortex, export a lockfile, apply one.
- **Deploy** shows how many changes are pending; clicking it lists them before applying, with Purge beside it. **Play** deploys and launches through the script extender. When an enabled plugin's masters are missing or load after it (the `missing_masters` finding, unless ignored), Play first says the game would crash at start and offers Sort with LOOT… (when a sort can fix it), Turn them off (one undo step) or Play anyway; after a fix it plays. Problems' `missing_masters` rows have the same Sort with LOOT… or Turn it off.
- **Nexus:** the header's account button signs in (or asks again when Nexus stops accepting the key), shows who is signed in and whether they have Premium, signs out, and sets rmm to open the website's download links. "From Nexus…" takes an `nxm://` link, a mod page link, a mod id or a collection link (the profile's own collection's link is an update), and "Check for updates" tags mods that have a newer file and lists them, each with Skip and Hold, and offers the profile's collection's newer revision. "From a link…" takes GitHub, ModDB and archive links, and for sign-in sites waits for the file from the browser (see Other sites).
- **MCP:** for AI apps that use rmm's tools (see "AI integration"). **Over HTTP, while this window is open**: Turn on/Turn off for the HTTP server on the open instance (remembered for the next window, and moved along when another instance opens), with its URL and the Claude Code command and JSON settings that carry its token. **Started by the app (stdio)**: the Claude Code command and JSON settings that run `rmm mcp -i <instance>`. Each snippet has Copy. Below them, the MCP settings (port, keeping sessions) and the instructions added to each role's prompt.
- **Add-ons…** lists add-ons with what they may do, installs one after showing its capabilities, removes one, runs its tools and shows its panels.
- **Settings:** rmm's settings (below) in sections, each saved as it changes (a refused value shows why and goes back), Reset all settings… (the MCP tab's too), and the window's own: theme (tokens are `light-dark()` pairs, so `data-theme` on the root picks one), compact rows, size (the webview's zoom), start tab, how often it polls for outside changes (or never), seconds a message stays, the Recent filter's days, asking before installing dropped files, and skipping the deploy preview. Those are kept in the window's storage. The downloads folder is the instance's and has Choose… and Default.
- **Install** from a file picker or by dropping archives or folders on the window. An archive is unpacked once, into the preview cache the install then reuses.
- **FOMOD wizard:** a mod with a FOMOD installer opens one step at a time. Each group says what it takes (choose one, one or none, at least one, any, all included), with radio buttons or checkboxes to match, and tags for Recommended, Required, "Can't be used" and "Might not work" (locked where the installer locks them). The side panel shows the option under the pointer or keyboard focus, with its picture (read from the installer by `fomod_image` and sent as a `data:` URL). After every change the core plays the whole installer again, so steps that depend on earlier choices appear or disappear, defaults and option types update, and the file count follows. If a change makes a later step's choice unusable, the later steps take their defaults. The mod is named after the installer's module name, and the choices are stored with it like the CLI and MCP installs. Hints mark options: on Skyrim SE, the one for the game's version (**Your game version** on an AE or pre-AE option, from the exe's version, which `fomod` returns as `game_version`) and the other (**Other game version**); and patches for enabled mods (**You have …**, matched on the mod or plugin name, or its initials as a word, as in USSEP; not the base game's plugins or the mod being installed). A click costs about 150 ms on the 3,000-mod fixture (the installer's file conditions are checked against every enabled mod).
- **No consoles:** the console programs rmm runs (curl, PowerShell, tar, certutil, Defender's `MpCmdRun`, the C# compiler) start through `rmm_core::hidden`, which sets `CREATE_NO_WINDOW`, so none opens a console over the window. Tools the user adds, and desktop shortcuts (`rmm launch --pause`, to show the deploy), keep theirs.
- **Live refresh:** the window checks the instance's files every 1.5 seconds (Settings) and reloads when the CLI or an AI over MCP changed them, one reload at a time. Renames and notes write `rmm-mod.toml` through a temp file in `mods/`, so they change the folder the window watches; the file keeps its time, which is the mod's install date.
- **One change at a time:** a click that comes while a change runs says which one is still running instead of doing nothing; Deploy shows neither "Deployed" nor an old count while it recounts; destructive confirmations use the danger style with Cancel focused.
- **First run:** open an instance folder, or create one for a detected game. Auto search adds game folders found on any drive, and "Choose the game folder…" takes one by hand (`game::identify`: the folder with the game's exe, or its Data folder). Each game found shows its exe's version, whether it's in a Steam library, and its drive's free space; the new-instance dialog gives the free space too, in red under 20 GB. Skyrim with a 1.6 exe is named Skyrim Anniversary Edition, here and in the window's title. A new instance is offered `<game's drive>\rmm\<game>`, where deploys link instead of copy; another folder on another drive, or under Program Files, gets a warning first. The first instance ever opens in the Simple view.
- **Getting started:** a list at the top of the Mods tab until everything on it is done or it's hidden (Settings brings it back): sign in to Nexus, let the website's "Mod manager download" buttons install here, the script extender, Address Library and a crash logger (Crash Logger SSE, or Buffout 4 or Buffout 4 NG by game version), and starting the game with Play. `launch::essentials` finds each in an enabled mod (the loader in `root/`, a `versionlib-`/`version-*.bin` or a crash logger DLL in `SKSE`/`F4SE/Plugins`) or in the game folder, and whether Play has run; `rmm info` and MCP `instance_info` include it. "Get it…" opens the mod's Files tab on Nexus and says which game version to pick the file for, since the newest file is often for a newer game than the one installed.
- **Language** (Settings, This window): English, Deutsch, Español, Français, Русский or 简体中文. The window is written in English; `ui/i18n.js` swaps its text for the chosen language's as it appears (a MutationObserver), from `ui/lang/<code>.json`, which maps each English text piece and tooltip to its translation. In a key, `{0}` stands for a part that changes; the part is translated too when it is text of its own (a nested sentence, a count), and a key starting with `#` is a count whose `{0}` is a number (`#{0} files`). Names (the mod and plugin lists' name cells, anything marked `translate="no"`), and messages from the game and rmm's engine stay as they are. Changing it reloads the window. Russian counts use one plural form.
- **Simple view** (Settings, This window) hides the Data, Tools and MCP tabs. It also hides the advanced filter chips, + Separator, the profile menu's import and lockfile items, and Settings' tool and test-run sections.
- **Downloads tab:** a Find box (by file, Nexus or mod name), and Delete… in red, apart from Install.

The window was checked by hand on Windows through WebView2's DevTools protocol; there are no automated UI tests.

## Settings (`crates/rmm-core/src/settings.rs`)

`settings.json` in rmm's config folder, read where each feature runs, so the CLI, the MCP server and the window share it with no restart. Every field has a default (`#[serde(default)]`); a missing or unreadable file means all defaults. `set` checks ranges first (`Settings::check`), `set_one` takes a dotted name and text (a string as is, a list as JSON or commas, anything else JSON), and `reset` puts one or all back. `rmm settings` and the window's `settings` / `set_settings` / `reset_settings` calls use them. Settings are not exposed over MCP.

- **Health:** `low_space_gb` (20; 0 never): Problems warns (`low_disk_space`) while the instance's or the game's drive has less free space than that.
- **Deploy:** `skip_extras` (on by default) keeps files that aren't for the game out of Data and the game root: `meta.ini`, `vortex_override_instructions.json`, `fomod/`, read-me's, licences and other documents (`.txt`, `.md`, `.pdf`, `.htm`… at a mod's top level, `readme`/`docs` folders), and a script extender's `src/`. Folders rmm made that a deploy leaves empty are removed. `exclude` drops matching files from the wanted set before the plan (a case-insensitive `*` glob on the path inside Data, or the file name when the pattern has no `/`); `method = "copy"` copies every file, and a linked entry counts as stale so the next deploy redoes it as a copy. Copies stay copies after switching back until a purge.
- **Launch:** `script_extender = false` starts the game's exe even with the loader installed (a warning says its plugins won't load); `args` are split on spaces, quotes kept together.
- **Instance:** `history.limit` caps the undo snapshots. `instance.toml` may set `downloads_path` (absolute), used by Nexus downloads and the Downloads list.
- **LOOT:** `refresh_hours`, the message `language`, `show_info` (LOOT's `say` messages as `info`), `sort_after_tools` (after a tool run adds plugins, `loot::place` puts only those where LOOT's sort would, each after the nearest plugin LOOT puts before it; the rest keep their order).
- **Health:** `hidden` kinds are dropped at the end of `check` (`health::KINDS` lists every kind with a description); `ba2_limit` replaces the worked-out Fallout 4 limit.
- **Test runs:** `window`, `dwell` and `timeout` are the defaults a scenario doesn't set; `keep_runs` deletes the oldest `test-runs/<start>` folders when a run takes screenshots; `screenshots` is the window's default.
- **Nexus:** `recheck_days`; `check_on_start` makes the window check quietly once signed in (a message only when there are updates).
- **Tools:** `timeout_mins` limits tool runs started from the window.
- **AI:** `role_instructions`, appended to each role's MCP prompt (the window's MCP tab).
- **MCP:** the window's `port`; `record_sessions = false` stops keeping AI apps' sessions as chats.
